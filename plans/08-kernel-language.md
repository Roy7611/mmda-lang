# 08 内核实现语言：Rust 单实现 vs 在 Java/C# 之上建语言层

> **问题（作者 2026-09-26）**：「我突然萌生一个想法，**是否在 C#/Java 之上弄一个解析语言更容易呢？**」
> 本文把"更容易"拆开算清楚，并给出不改架构也能拿到那份"容易"的做法。

## 1. 先把想法拆成三条互斥的路线

| 路线 | 含义 | 现状 |
| --- | --- | --- |
| **A 宿主实现** | M 语言的词法/语法/校验/**求值**用 **Java 或 C#** 写，住在宿主里 | 新提议 |
| **B 宿主内嵌脚本引擎** | 在宿主之上跑一门脚本/DSL（Roslyn scripting / GraalJS / Jint / 自研解释器） | **✔ 已否**（[`../PLAN.md`](../PLAN.md) §6.3-34/35/36） |
| **C 独立内核 + 对外两面** | Rust 单实现，对外 **C ABI（cdylib）+ WASM**；宿主只暴露能力函数 | **✔ 已裁**（[`../README.md`](../README.md)、[`../PLAN.md`](../PLAN.md) §6.3-40） |

## 2. 对照表（同一条判据看三条路线）

| 判据 | A 宿主实现（Java/C#） | B 内嵌脚本引擎 | C Rust 单实现（现状） |
| --- | --- | --- | --- |
| **起步速度** | ⭐⭐⭐ 最快（宿主就在手边） | ⭐⭐⭐ 最快 | ⭐ 最慢（要自建词法/语法/诊断） |
| **三端一致性** | ❌ 必须写**两遍**（Java + C#）—— 正是 [`../PLAN.md`](../PLAN.md):63 明令禁止的"双实现必然漂移" | ❌ 三端各写一遍（§6.3-34 已实测否掉） | ✅ 一份实现，三端同语义 |
| **实现不外泄（护知识产权）** | ❌ Java/C# 易反编译 | ❌ 同 | ✅ 内核以二进制/WASM 分发 |
| **语义/规则单一真源** | ❌ 解析在 Java、生成在 C#、门禁在哪端？ | ❌ 同 | ✅ 一份语法树喂 LSP / 校验 / 生成 / 求值 |
| **调试与被审** | 宿主工具链成熟 | 同 | 需自建（已在 [`04-verification.md`](04-verification.md) 设计） |
| **宿主能力访问** | ✅ 直接 `new` EntityFactory | ✅ 同 | ⚠️ 需 P6 嵌入通道暴露（**能力函数按白名单**）—— 但这是**能力暴露**问题，不是**语言实现**问题 |
| **沙箱** | ❌ 无（Java 21 无 `SecurityManager`，已实测） | ❌ 同 | ✅ WASM 档天然可沙箱 |
| **启动/部署** | 无额外运行时 | 无 | 内核 + WASM 运行时（约 1 个依赖） |
| **性能** | 中（JIT 预热后可用） | 中 | 高（编译型，parse/check 目标已量化） |
| **一次性成本** | 低 | 低 | 高（M0–M4） |
| **三年后成本** | ❌ 高（两份实现 + 双倍回归 + 语义漂移） | ❌ 最高 | ✅ 低（一份实现 + 一份回归） |

## 3. 为什么"宿主实现"在**这个项目**里特别贵（四条都是你已裁的口径）

1. **三端一致是首要目标**（[`../PLAN.md`](../PLAN.md) §工程目标）。宿主实现 ⇒ Java 与 C# 各一份 ⇒ **"两套语义必然漂移"**（你在 PLAN 里正是用它否掉 C+Rust 双实现的，逻辑同样适用于 Java+C#）。
2. **实现不外泄**：你已拍「核心算法与实现不进 Java/C#（易反编译），下沉 Rust native（cdylib + C ABI / Panama / P-Invoke）或服务化，三端宿主只留薄适配层」。宿主实现**直接把这句作废**。
3. **同一棵语法树的四个消费方**：LSP（诊断/跳转/补全）、`m check`（硬门禁）、生成器、脚本求值 —— 宿主实现会把它们分到不同语言/进程里，**语义真源立刻分叉**（这恰是上一轮"正则扫描"翻车的形态）。
4. **宿主语言能力不是免费午餐**：`beforeXxx/afterXxx` 要用 m 写、Action 走 `IAction`（D16–D20）—— 这些**恰恰要求"语言"独立于宿主**；住在宿主里就得为每端重做一遍"语言→宿主"的映射。

## 4. 业界的三种既有形态（"在宿主之上弄解析语言"到底能成什么样）

| 形态 | 例子 | 能拿到什么 | 拿不到什么 |
| --- | --- | --- | --- |
| **编译期宏 / 注解处理器** | Lombok、MapStruct、Rust proc-macro | 宿主同权、零运行时 | 只活在编译期，做不了"元数据驱动运行时" |
| **内嵌脚本引擎** | GraalJS、Roslyn scripting、Jint、Lua | 起步最快、宿主同权 | **三端各一套 + 无沙箱 + 语义漂移**（§6.3-35 已实测：JDK 21 内存编译 19–34 ms、Roslyn 冷 344 / 热 31 ms；但**脚本能读环境、列目录、起进程**） |
| **独立内核 + FFI/WASM** | rust-analyzer、swc、tree-sitter、SQLite | 单一语义、可分发、可沙箱、实现不外泄 | 起步慢（要自建解析与诊断） |

**MMDA 要的是"元数据即真源 + 三端一致 + 实现不外泄"，只能落在第三类** —— 这不是偏好，是被目标筛出来的。

## 5. 但你的直觉里有真东西：**那份"容易"可以不改架构拿到**

| 折中 | 做法 | 拿到什么 |
| --- | --- | --- |
| **折中 1（推荐）** | **spike：原型用 Java/C# 快速试语义，产品仍 Rust** —— 一次性、不进仓库，产物是**用例与规范修正**（`spike` 纪律：验证完就扔） | 快速试错的全部好处，风险留在草稿里 |
| **折中 2（已裁 D19）** | 首版钩子只吃**声明式子集**（元数据能表达的），完整 m 内联等内核通道 | "IDE 里写 m"的体验早兑现一部分 |
| **折中 3** | **优先做 WASM 面**（一份 Rust 内核编成 wasm，三端各嵌一个运行时：Java 侧 Chicory/wasmtime-java、C# 侧 wasmtime-dotnet），**Panama / P-Invoke 降为次选** | 免掉"每端一套原生绑定"，部署更简单；`§6.3-40` 已把 WASM 定为内核侧形态 |

## 6. 什么时候真的该换路线（判据写死，省得反复纠结）

只有满足**全部**三条，才值得改宿主实现：

1. **放弃三端一致**（只做一端，或接受三端各一套语义）；
2. **接受实现可被反编译**（护城河改由服务化承担）；
3. **接受语言服务与生成器不共享同一棵语法树**（LSP、门禁、生成各自解析）。

三条里只要有一条不成立 —— **维持 C（Rust 单实现）**，用 §5 的折中拿速度。

## 7. 待你拍（D26）

- **A** 维持 **Rust 单实现**（现状），靠 spike + 声明式子集提速（**建议**）
- **B** 先做 spike：用 Java 或 C# 快速原型试语义，**产品仍 Rust**
- **C** 改宿主实现（Java/C#）：需同时接受 §6 的三条让步

## 8. LLVM 值不值得借用（✔ 作者 2026-09-26 提问：**是否在 C#/Java 之上弄解析语言更容易** 的续问）

> 作者附 [llvm.org](https://llvm.org/)（当前 LLVM **23.1.2**，2026-09-22；许可 = Apache 2.0 with LLVM exceptions）。仓内 grep：**`doc/` 与 `PLAN.md` 全篇 0 处提及 LLVM**（唯一相关的原生路径是 [`../doc/protection.md`](../doc/protection.md) 的 **Rust cdylib + Panama / P-Invoke + FlatBuffers**，与 `PLAN.md` §6.3-40 的 **WASM 组件（wasmtime）**）。

### 9.1 逐个子项目对账（LLVM 是"伞项目"，别整体看）

| LLVM 子项目 | 对 MMDA 有用吗 | 判据 |
| --- | --- | --- |
| **LLVM Core**（IR / optimizer / codegen） | ❌ 主链路无用 | 我们的产物是 **Java / C# / TS 源码 + DDL**，**不是机器码**；SSA 优化与 CPU 指令选择对"生成源文件"零作用 |
| **MLIR**（多级 IR / dialect / lowering） | ⚠️ **思路有用、工程不值** | 它解决"多级 IR + 多目标 lowering"；我们只有 **`m-model` → IR → emitter** 三层（[`01-stack.md`](01-stack.md) §3），自己写更省；引入 = C++ 构建链 + 巨量依赖 |
| Clang / libc++ / libc / LLD / BOLT / OpenMP / polly | ❌ 无关 | C/C++ 工具链与链接器领域 |
| LLDB | ❌ 无关 | 原生调试器；调 Rust 内核用 lldb/gdb 即可 |
| **compiler-rt / sanitizers** | ✅ 已在用（间接） | ASan / TSan 随 Rust 工具链自带 |
| **klee**（符号执行） | ❌ 过重 | 要验"硬门禁完备"，用例 + 变异测试更便宜（[`../doc/testing.md`](../doc/testing.md) 已有变异测试口径） |

### 9.2 最关键的一条：**你已经借了 LLVM —— 通过 Rust**

- `rustc` 的后端默认就是 **LLVM** ⇒ 内核（Rust）本身已在吃它的优化与代码生成；**"想把算法变快/变原生"= 写 Rust**，不需要直接依赖 LLVM API。
- 直接依赖的代价是实打实的：`llvm-sys` / `inkwell` 这类绑定要**锁死 LLVM 大版本**（LLVM 半年一个大版本、两个月一个小版本），换来的是**构建时间 + 二进制体积 + 持续升级负担**。
- 若哪天要给脚本 / 数据流算子做 **JIT 原生化**，你已裁的 **WASM 组件（wasmtime）** 就是那条路 —— **wasmtime 自带 Cranelift JIT，不需要 LLVM**；只有在"极致优化 + 愿意承担构建分发成本"时才谈换后端，留口子即可。

### 9.3 值得"借用"的不是 LLVM 的代码，而是它的五个做法

| LLVM 的做法 | 我们的对应落点 |
| --- | --- |
| **分层 IR + lowering** | `m-model` → IR → 各端 emitter（[`01-stack.md`](01-stack.md) §2/§3）；多方言时借 MLIR 的 **dialect 思路**，但不引 MLIR |
| **每阶段 verifier** | 硬门禁 + `mmda gen --check`（生成物指纹校验，[`06-codegen.md`](06-codegen.md) §2） |
| **LangRef 单页规范** | `doc/` 单点真源（关键字/注解表从 `doc/` 提取，[`02-parser.md`](02-parser.md) §3.1） |
| **lit / UI 测试** | 用例内嵌期望 `//~ ERROR M0xxx at L:C`（[`04-verification.md`](04-verification.md) §4） |
| **clang 级诊断文化** | 诊断结构 = 码 + span + 主次标签 + 修复建议（[`02-parser.md`](02-parser.md) §5） |

### 9.4 什么情况下才真该引 LLVM（三条判据，全中才动）

1. **产物从"源码"变成"原生机器码"**（自造通用编程语言的编译器 / 真 AOT 的 DSL→native）；
2. **需要极致的 JIT 优化**，且认定 Cranelift 不够用；
3. **有人能长期跟 LLVM 的版本节奏**（否则就是自己给自己上维护枷锁）。

**结论**：**不把 LLVM 引进产品依赖；抄它的做法；"LLVM 能带来的好处"你已通过 Rust（LLVM 后端）+ Wasmtime（Cranelift JIT）拿到。**
