# 02 词法与语法设计

> **前置**：解析策略与树形态待拍（[`05-decisions.md`](05-decisions.md) **D1 / D2**）。本文按 **D1=A（手写）、D2=A（无损 CST + typed AST）** 起草。

## 1. 输入事实（实测，2026-09-26）

语料 = `E:\Dev\mmda-architect\examples\mmda-mes`：

| 项 | 实测值 |
| --- | --- |
| 语言文件 | **372** 个：`.mm` 215 · `.me` 113 · `.ms` 41 · `.ma` 2 · `.mi` 1 |
| 项目清单 | `mmda-mes.mmda` = **JSON**（`{` 开头） |
| 编码 | **UTF-8，无 BOM**（首字节 `2f 2f 2f` = `///`） |
| 行尾 | **CRLF** |
| 顶层关键字（`.mm` 内） | `record` **191** · `view` **24**（其余 partType 在 `.me` / `.ms` / `.ma` 内） |
| 工具链 | `cargo 1.95.0` / `rustc 1.95.0` 已就绪 |

**硬约束（由上面推出，不是口味）**：CST 必须**逐字节保存空白、缩进、注释与 CRLF** —— 否则「图形改一个属性 → 回写文本」会把全文件的行尾和缩进洗掉，diff 爆炸。

## 1.1 语料的定位（✔ 2026-09-26 作者纠正：它不是基准）

> 作者原话：「**项目 372 文件，你管它干嘛，那是历史逆向工程出来的，我语法还在调整呢**」。

| 语料**可以**用来 | 语料**不许**用来 |
| --- | --- |
| ① **冒烟**：解析器对真实体量的输入不 panic、每条诊断都能定位 | 当**验收基准**（不设「372 文件 0 error」这类门禁） |
| ② **语法漂移报告**：列出「语料里出现、但现行语法已不吃」的写法，按文件归类 —— 这本身就是**迁移工具的输入** | 冻结成"正确性快照"（语法仍在调整，冻结即锁死错误写法） |
| ③ **性能负载**（文件量 / 体积真实） | 拿来反推语法规则 |

**验收基准 = `doc/` 规范 + `errata` 已裁项，逐条落成用例（正例 + 反例）**：你改语法 → 改 `doc/` → 改用例 → 跑绿，实现跟着规范走。

## 2. 词法（`m-syntax::lexer`）

| Token 类 | 内容 | 要点 |
| --- | --- | --- |
| 标识符 / 限定名 | `Order`、`base.Material`、`XMetaObject` | 限定名 `A.B` 在词法层**不分段**（一个 token），语义层再切 |
| 注解 | `@Ref`、`@Partitioned`、`@Index`、`@Computed`、`@Unique`… | 保留 `@`；大小写不敏感（[`../doc/lang/datatypes.md`](../doc/lang/datatypes.md) §1 已裁） |
| 数字字面量 | `10000`、`0x000F_FFFF`、`0X7f_ff`、`0o755`、`0b1010` | **十 / 十六 / 八 / 二**；**`_` 分组**；**大小写不敏感**；词法层直接产出**数值**（✔ 2026-09-25 作者：**没有位数/大小写规范化问题**） |
| 区间与 `..` | `[a,b]`、`(a,b)`、`[a,b)`、`(a,b]`、`a..b`、`..b`、`a..` | `..` = **C# `Range` / `Index` 语法**（**不是「省略式」**）；`a..b` 取 C# 语义**左闭右开**（⏳ 见 D-段，`05-decisions.md` D12） |
| 字符串 | `'|'`、`"…"` | 保留原始引号与转义写法 |
| 注释 | `///`（文档）、`//`、`/* */` | **进 CST**（注释是文档真源的一部分） |
| 换行 / 空白 | CRLF、缩进 | **进 CST**（round-trip 的命根子） |
| 关键字 | `record` / `view` / `enum` / `stm` / `converter` / `import` / `auth` / `module` … | 关键字表**从 `doc/` 生成**（单一真源），不手抄 |

**两条可测试的不变量**：
1. **token 拼接 == 原文件字节**（lexer 无损的第一道证明，M1 起跑）；
2. 数字字面量的**数值等价断言**（`0x000F_FFFF` == `0X7f_ff` == `1048575`）。

## 3. 语法（`m-syntax::parser`）

- **partType 判据 = 文件内容的首关键字**（[`../PLAN.md`](../PLAN.md) §6.3-1 已裁），扩展名只作提示与图标 —— 这正好让「一文件可以放多个对象」（✔ 2026-09-25 作者）自然成立：**一个文件 = 一个 part 序列**，不是"一个文件一种对象"。
- **递归下降**：每个 partType 一个 `parse_xxx()`；注解统一走 `parse_annotations()`（前缀 + 独立行两种位置）；字段/成员走**声明式驱动**（从 `doc/` 抽出的形式表生成 `match`，避免"文档改了代码没改"）。
- **Pratt**：只用于表达式位（`@Computed <expr>`、`@Index` 的列表达式、默认值、`where` 条件）—— 前缀/中缀/后缀 + 优先级表，一处定义。
- **错误恢复（IDE 的命门，必须一开始就做）**：
  - 同步集 = { 顶层 partType 关键字, `}`, 下一行行首的注解, 文件尾 }；
  - 一个 part 内出错 → 跳到下一个同步点继续，**同一文件报多个错**（不许"一个错字全文件变红"）；
  - 每次恢复都记进 CST（错误节点），保证树仍可遍历、位置仍精确。
- **不在语法层判语义**：`@Ref base.Material` 目标是否存在、段是否重叠、`unique` 的租户语义 → 全在 `m-check`（语法层只保证形态）。

### 3.1 语法调整期的设计要求（语法还在动，这是硬需求）

1. **单点表**：关键字表、注解名表、partType 形式表**从 `doc/` 提取**（一处定义 → 生成 `match`），不散落在各函数里 —— 你改规范，我改一处。
2. **用例即契约**：每个语法点一条正例 + 一条反例（[`04-verification.md`](04-verification.md) §1 P1）；语法变更 = **改用例**，解析器代码里**不写兼容分支**。
3. **不认识就报错，不许猜**：遇到未收录写法 → 报 `M02xx`，给行列 + 「期望什么」；**不静默容忍**（静默容忍会把语法错误藏进生成物）。
4. **可对账**：诊断与报告里带**实现所依据的规范版本**（`doc/index.md` 的草案号），便于判断"这条规则是什么时候的"。

## 4. 两棵树（D2=A）

```
Token { kind, span: TextRange, raw: () }        ← 空白/注释/CRLF 都在
  └ Node { kind, children: Vec<Element>, span }  ← 无损 CST（Element = Token | Node）
      └ typed AST: Record { name, annos, fields: Vec<Field>, span }  ← 语义层用的视图
```

- **CST 无损**：`cst.text() == source` **逐字节成立**（M2 的验收条款）；
- **typed AST**：手写视图（不生成访问器），字段是真正的类型而不是 `Vec<String>`（旧实现的反面教材：`RecordAst.fields: Vec<String>`）；
- **升级路径**：如果将来要真正的细粒度增量，CST 的 API（子节点按 `kind`/`span` 查询）刻意做成与红绿树同形，换 `rowan` 只动 `m-syntax` 内部。

## 5. 位置与诊断

- **位置**：`TextRange { start: u32, end: u32 }`（字节偏移，半开区间）；行/列由 `LineIndex`（预计算行首表 + 二分）换算 —— 报告一律给 **`<file>:<line>:<col>`**（可点击）。
- **诊断结构**：`Diagnostic { code: &'static str, severity, message, primary: (span, msg), labels: Vec<(span, msg)>, fixes: Vec<Suggestion> }`。
- **错误码分段**（D7，建议值）：

| 段 | 范围 | 例子 |
| --- | --- | --- |
| 词法 | `M01xx` | `M0101` 数字字面量非法（`0x` 后无数字） |
| 语法 | `M02xx` | `M0203` 期望 `;` |
| import | `M03xx` | `M0301` 同名 import / `M0302` 目标不存在 |
| 分区与段 | `M04xx` | `M0401` 同组段重叠 / `M0402` 非组内成员写了范围（warning） |
| 唯一性 / 约束 | `M05xx` | `M0501` 多租户实体上的全局唯一冲突（语义提示） |
| 类型与关系 | `M06xx` | `M0601` `@Ref` 目标类型不匹配 |
| 生成 | `M07xx` | `M0701` 生成目标不支持的类型映射 |

## 6. 增量与缓存

### 6.0 三档，只做前两档

| 档 | 做什么 | 什么时候 |
| --- | --- | --- |
| **0 全量** | 进程启动后全量解析，无缓存 | **现在（M0–M5）** |
| **1 文件级** | 内容 hash 未变 → 复用上一轮 CST + 诊断；依赖图边 = `import`；脏文件重解析后只重检查**受影响的符号** | M6 |
| **2 子树级** | 红绿树（green 不可变 + 哈希驻留 / red 惰性视图 + 父指针偏移缓存）+ salsa 式 memo 查询 | **门槛见 §6.3，未中不上** |

### 6.1 为什么现在不上红绿树（✔ 作者 2026-09-26 提问）

1. **它解决的问题不属于这一阶段**：红绿树卖的是「**编辑时**子树级重解析」。M0–M5 是**批处理**（起进程 → 读文件 → 出诊断 / 生成 → 退出），**没有"上一版"可复用** ⇒ 绿树的收益是 0，建树的成本全价照付。
2. **它的复杂度不在代码量，在内存布局里的不变量**：green 不可变 + 哈希驻留、red 带父指针 + 偏移缓存 —— 两棵树的一致性必须自己守（red 懒建、父指针重建、偏移缓存失效）。**出事症状是「补全偶尔给出旧结果」**：不可复现、无定位、被"重启 IDE 就好了"掩盖。P2 的验收筹码是**可验证**（round-trip 逐字节 + 用例集全绿），拿它换增量一致性 = **用强项换弱项**。
3. **配套债是一整套**：salsa 式 memo 查询 / 依赖追踪 / **取消**（编辑打断上一次计算）/ 版本与 `Durability` / LRU 内存上限 —— rust-analyzer 是**多年 + 巨量代码**磨稳的，第一版没有这个预算。
4. **我们场景的增量收益小一个数量级**：rust-analyzer 面对几十万行 Rust + 宏展开，全量重解析真到秒级，所以**必须**增量；我们的输入是 **372 个元数据文件（`.mm` 215 / `.me` 113 / `.ms` 41 / `.ma` 2 / `.mi` 1）、单个几百字节～几 KB** ⇒ **全量解析是毫秒～几十毫秒级**。
5. **我们的语言形态天然省掉一整类复杂度**：M 是声明式、**无函数体**（算法体不在语言里）⇒ 不存在"大函数体懒解析"这种需求，单文件全解析本来就便宜。
6. **最要紧的一条：语法还在调整期**（作者原话：「我语法还在调整呢」）。绿树的 Kind 表 / 驻留结构 / 增量边界会被**每一次语法改动**波及 —— **最贵的抽象要建在最稳的接口上**，而语法现在是全项目最不稳的一面。正确顺序是：**先全量 → 用 P1 用例集把语法冻住 → 再谈增量**。

### 6.2 为什么"现在不做"不等于"欠账"（接口已同形）

- 对外契约已经是终态：`TextRange` 字节偏移 + **无损 CST** + 按 `kind` / `span` 查询的 API（§4），且 §4 已写明「**CST 的 API 刻意做成与红绿树同形**」。
- 将来换实现（`rowan` 或自写 green/red）**只动 `m-syntax` 内部**，上层（校验 / 生成 / LSP / 格式化）**一行不改**。

### 6.3 真要上细粒度增量的门槛（四条**全中**才动）

1. 全量解析 **P95 > 200 ms**（单文件 + 全项目），且 profiling 证明时间**真在解析**，不在语义检查或生成；
2. 编辑器里出现**可感知卡顿**（键入 → 诊断 > 150 ms）且「防抖 + 取消 + 只报当前文件」救不回来；
3. 项目规模进入**数千～万级文件**（单模块栈 + 平台模型，不是现在的 372）；
4. **已经上了档 1（文件级增量）仍然不够**。

- 只中 1 / 2 ⇒ 先做**档 1**（成本低一个数量级，收益的大头）。
- 四条全中 ⇒ 才引入**档 2**（`rowan` + salsa 或等价物）。

### 6.4 现在明确不做

不做红绿树、不做 salsa、不做跨文件并行（**372 文件单线程 < 1 s** 是目标，先测再谈优化）。
