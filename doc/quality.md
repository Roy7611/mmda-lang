# 质量模型与自动评估（Quality Model）

> **这份文档要解决什么**：验收标准不能只有"用例跑绿了"。要覆盖软件质量的方方面面、并且**尽量自动评估**，就得有个骨架——用 **ISO/IEC 25010**（SQuaRE 的产品质量模型）当骨架，把每个质量特性**映射到 MMDA 里真正能算出来的信号**，并诚实标注哪些能自动、哪些只能人评。
> 状态：草案（2026-09-24）· 与 [`testing.md`](testing.md)（用例与验收）、[`workflows.md`](workflows.md)（职责 / 变更分级 / 签字）、[`targets.md`](targets.md)（capability）、[`presentation.md`](lang/presentation.md)（渲染描述）联动。
> 标准依据：ISO/IEC 25010:2011（8 特性）→ **2023 版（9 特性）**：`usability → interaction capability`、`portability → flexibility`、**新增 `safety`**，子特性上新增 `inclusivity` / `self-descriptiveness`（交互能力）、`resistance`（安全性）、`scalability`（灵活性），`maturity → faultlessness`、`UI aesthetics → user engagement`、`accessibility` 拆为 `inclusivity + user assistance`（来源见文末 §8）。

---

## 0. 三条原则

1. **质量需求必须写成可判定的声明**，否则无法自动评估。例：「列表页 P95 < 500 ms」「敏感字段不得出现在列表视图」「财务单据必须留审计字段」——声明进模型或 Codegen Profile，工具据此算。**没写成声明的质量要求，等于没有验收标准。**
2. **可判定性分级（本文的核心机制）**：A 设计期静态可判定 / B 生成后可判定 / C 运行期才能测 / D 只能人评。**A、B 进硬门禁；C 进定期仪式（发布前基准/演练）；D 进 AI 报告 + 人签字。** 并且持续把 D 往 A/B 迁移——这是"自动评估"唯一的现实路径。
3. **门禁看"证据有没有 + 达标没有"，报告看趋势**：质量分不打成一个成绩给全员看（那是凑数），门禁只断言 A/B 项；报告用九维雷达图看走向，并显式列出"未评估"项——**不假装算过**。

## 1. 25010 → MMDA 的信号映射

**等级**：A 设计期静态 / B 生成后静态或跨端用例 / C 运行期实测 / D 人评。

### 1.0 标准谱系与命名对照（读外部资料时别被名字带偏）

| 版本 | 特性数 | 特性名（原文口径） | 备注 |
| --- | --- | --- | --- |
| **ISO/IEC 9126:1991** | 6 特性 / 27 子特性 | 功能性、可靠性、易用性、效率（译作"频率特性"）、可维护性、可移植性 | 最早的软件质量模型；定量度量类的论文多基于它 |
| **ISO/IEC 25010:2011** | 8 特性 | 功能适合性、性能效率、兼容性、**可操作性**、可靠性、安全性、可维护性、**可移植性** | 中文资料（含内部 PPT）多数停留在这里 |
| **ISO/IEC 25010:2023** | **9 特性** | 交互能力（原 usability）、灵活性（原 portability）、**新增 `safety`（与 security 分开）** | **本文采用的版本**，命名见 §1.1–§1.9 |

→ 读外部材料时的对照规则：**"可操作性 / 易用性" = 交互能力，"可移植性" = 灵活性，"频率特性" = 性能效率**。同一份报告里不要混用两代名字。

### 1.1 功能适合性（Functional suitability）

| 子特性 | MMDA 里可自动的信号 | 等级 | 门禁 |
| --- | --- | --- | --- |
| 功能完备性 | 需求 `REQ-x` → 模型声明 → 用例的三级追溯完整率；`orphan` 用例数（[`testing.md`](testing.md) §6） | A | 硬（需求覆盖 ≥ 90%） |
| 功能正确性 | 机械用例（长度/引用/迁移矩阵/权限矩阵）全绿；三端结果一致 | B | 硬 |
| 功能适合性 | 每条 Action 有前置状态与授权角色；每个 Feature 有归属模块（**无主功能 = 不合格**） | A | 硬 |

### 1.2 性能效率（Performance efficiency）

设计期能算的**风险信号**（不需要跑起来）：

| 信号 | 怎么算 | 等级 |
| --- | --- | --- |
| 查询路径缺索引 | 视图/搜索/排序用到的字段是否都有 `@Index`（含组合顺序） | A |
| N+1 风险 | 列表视图里引用了 `@Many` / 多层 `@Ref` 而未声明分页或批取 | A |
| 缺分区键 | 大表（按声明规模分类）是否声明 `@Partitioned` | A |
| 大类字段误用 | `text`/`blob` 出现在索引、排序、where 条件里 | A |
| 分页缺失 | 列表类视图未声明分页或 `@Many` 无上限 | A |
| 目标值缺失 | Profile 里未声明时间行为/吞吐/容量目标 | A |

| 子特性 | 运行期度量 | 等级 |
| --- | --- | --- |
| 时间行为（P95/P99）、吞吐 | 生成物基准测试 + 生产监控 | C |
| 资源利用（CPU/内存/连接池） | 同上 | C |
| 容量上限 | 压测 | C |

> **采集项清单见 §2.3；默认门槛（响应 ≤ 5 s / 并发 ≥ 500·800 / TPS ≥ 80）见 §2.2**。

> **关键**：把 A 类风险信号当门禁（它们和"性能好"强相关，且零环境依赖），把 C 类实测当发布前仪式。**不要用 C 的不确定性去拖累 A 的判定**。

| 子特性 | 信号 | 等级 |
| --- | --- | --- |

| 威胁建模 | 渗透测试、威胁建模结论 | D（转 A：把结论写成"必须拒绝/必须审计/不得出现"的声明，即可自动检查） |

## 2. 可判定性分级与"把 D 变 A/B"的做法

| 等级 | 定义 | 归宿 |
| --- | --- | --- |
| **A** 设计期静态 | 只读元模型/Profile 就能算 | 硬门禁（CI 必过） |
| **B** 生成后可判定 | 对生成物做静态分析，或三端跑同一批用例 | 硬门禁 |
| **C** 运行期实测 | 需要真环境与负载 | 发布前仪式 + 看板趋势 |
| **D** 只能人评 | 价值、威胁、可用性主观面 | AI 报告 + 人签字 |

**迁移三例（这是"自动评估"的真正工作）**：

1. 「界面好不好用」→ 拆成 **呈现描述完整性（A）** + **验收单可读性抽查（B：业务人员能否看懂）**；剩下的主观部分留在 D，并明确"不阻塞交付"。
2. 「性能够不够」→ **目标值声明（A）** 与 **实测（C）** 分开报告。声明缺失本身就是不合格（你没说要多少），这比"没测"更容易自动化。
3. 「安全威胁」→ 威胁建模的结论**写成声明**（必须拒绝 / 必须审计 / 不得出现 / 必须二次确认），声明可自动检查（A）；渗透与建模过程留 D。

### 2.1 三层度量模型与加权聚合（"打分"怎么做才可复算）

来源：程诺、万琳、张威《基于量化指标分析的软件质量度量方法》，《北京化工大学学报》第 34 卷增刊 I（2007），127–129 页（本地扫描件：`D:\项目\2026 mmda\基于量化指标分析的软件质量度量方法.pdf`）。该文在 ISO/IEC 9126 基础上给出**三层度量模型**与加权聚合方法，正好补上本文此前缺的"定量层"。

```
可算信号（度量元） --算术平均--> 质量子特性 V_2j --加权平均--> 质量特性 V_ci --加权--> 综合 V
```

| 步 | 公式 | 说明 |
| --- | --- | --- |
| ① 度量元 | 按适用性选择并计分 | 本文 §1 各表里的**一个 A/B/C 信号就是一个度量元** |
| ② 子特性 | `V_2j = (1/n) Σ_k V_jk` | 该子特性所辖**适用**度量元的**算术平均** |
| ③ 特性 | `V_ci = Σ_j (V_2j × W_2j)`，`Σ_j W_2j = 1` | **加权平均** |
| ④ 综合 | `V = Σ_i (V_ci × W_ci)`，`Σ_i W_ci = 1` | 加权和 |

论文算例（可靠性；权重由**特征根法**即 AHP 判断矩阵求得）：判断矩阵 `[[1, 1/3, 1], [3, 1, 3], [1/3, 1/3, 1]]`（成熟性 / 容错性 / 易恢复性）→ 权重 `(0.6, 0.2, 0.2)`，测量值 `(0.68, 0.5, 0.7)` → `V_c2 = 0.68×0.6 + 0.5×0.2 + 0.7×0.2 = 0.648`。

**落到 MMDA 的三条收窄**（论文的 `V` 是给管理者的一个综合分；我们的场景要防"一个分数掩盖违规"）：

1. **权重是项目资产**：写在 Codegen Profile 的 `quality.weights:`（与 §7-1 的目标值同处），**AHP 判断矩阵一并留档**，权重改动进 changelog（谁改的、为什么改）。
2. **只有 A/B/C 的可算项进加权**，**D 类不参与**（主观分混进数字会让结果看起来精确、实际不可复现）；D 项在报告里单列 + 签字。
3. **`V` 只进趋势 / 排序 / 对比，不进硬门禁**（与 §0 原则 3 一致）：门禁仍**逐项**断言 A/B 达标，**不允许用综合分"抵消"某个硬项违规**。

### 2.2 默认质量目标基线（阈值起始值，可被项目覆盖）

来源：`D:\项目\2026 mmda\软件质量.pptx`「可量化的」页（其引用出处见该页：teambition / CSDN / 腾讯云 / 阿里云）。这是**行业常见默认值**，作为 Profile `quality.targets:` 的起始值：

| 维度 | 指标 | 默认门槛 | 等级 |
| --- | --- | --- | --- |
| 可靠性 | 可用性 =（总耗用时间 − 停机时间）/ 总耗用时间 | **≥ 99.9%** | C |
| 可靠性 | MTTF（平均失效前时间） | **≥ 10 天** | C |
| 可靠性 | MTTR（平均修复时间） | **≤ 30 分钟** | C |
| 可靠性 | MTBF（平均故障间隔）= 总操作时间 ÷ 故障次数（**≈ MTTF + MTTR**） | **≥ 10 天/次** | C |
| 性能效率 | 响应时间（平均） | **≤ 5 s** | C |
| 性能效率 | 并发用户数 | **≥ 500（单机）/ 800（双机）** | C |
| 性能效率 | TPS（每秒事务数） | **≥ 80** | C |

换算关系（交叉校验与容量推算）：**并发数 = QPS × RT**，`QPS = 并发数 ÷ RT`。

用法两条：**① 声明缺失本身就是 A 类不合格**（§1.2「目标值缺失」）；实测达标与否是 C 类，进发布前基准与看板。**② 目标值按环境分档**（开发 / 预发 / 生产）——不要拿生产的 99.9% 去卡开发环境。

### 2.3 运行期指标清单（14 项，采集面）

外部资料给出的通用 14 项（`软件质量.pptx`「14 个指标」页，原 dzone 文章）：响应时间、请求率（RPS）、用户交易、单位时间虚拟用户数、错误率、等待时间（TTFB）、平均加载时间、峰值响应时间、并发用户、通过/失败交易、吞吐量（KB/s）、CPU 利用率、内存利用率、用户会话总数。

映射到三个采集面（`mmda quality measure --runtime`）：

| 采集面 | 能出的指标 |
| --- | --- |
| 网关 / HTTP | 响应时间、TTFB、RPS、错误率、吞吐量、并发 |
| 宿主资源 | CPU 利用率、内存利用率、连接池 |
| 业务与前端 | 用户交易、通过/失败交易、会话数、平均 / 峰值加载时间 |
| **总线 / 集成**（[`event_bus.md`](lang/event_bus.md) §12.1） | **入**：接收速率、解码失败率、迟到率、积压；**流**：节点级失败率、算子状态大小、检查点耗时；**出**：投递成功率、端到端时延 P50/P95/P99、外部端点响应时间、重试次数；**可靠**：失败队列长度、重放次数、幂等命中数、对账差异数；**租户**：按租户吞吐与配额 |

两条可判定的边界：

> **采集面到出口的落地见 [`operations.md`](operations.md)**（五层监控模型、**零手写打点**清单、与 Prometheus / Zabbix / 夜莺的集成、告警内容规范）。

- **峰值响应时间 ≫ 平均** ⇒ 至少有一个问题组件——**只看均值不算合格**，报告里 P95/P99 与峰值同列。
- **页面加载 > 3 s 用户倾向放弃** → 前端性能预算可自动查（**唯一渲染方 = mmda-vue**）：静态资源体积 + 首屏字段数（`MetaUi` 声明的列数与控件类型）。

## 3. 质量报告与门禁

| 命令 | 作用 |
| --- | --- |
| `mmda quality report [--lang zh]` | 九维 × 子特性报告：每项给「证据在哪 / 等级 / 达标或未达标或未评估」+ 趋势；给业务与管理层看 |
| `mmda quality gate` | CI 门禁：只断言 A/B 项；C/D 项输出「待测 / 待评」清单 |
| `mmda quality diff <变更>` | 本次变更对九维的影响（哪几项达标度下降） |

**与 [`testing.md`](testing.md) 的关系**：用例通过率、覆盖率、变异存活率、用例质量分是**功能适合性 + 可维护性**的输入信号，不替代质量报告——报告管"面"，用例管"点"。

**体验面（UX）检查的落点（✔ 已裁 2026-09-24）**：**尼尔森十原则的 A 类子集**与**无障碍可自动化子集**（语义标签 / 焦点顺序 / 错误文本）进 **`mmda check` 出 warning——不阻断、不进 `mmda quality gate`**（与命名检查同档）；清单、判据与「静态可判定 vs 运行期实测」的分界见 [`ux.md`](ux.md) §4 / §5 / §8。**运行期体验度量**（任务完成率、校验失败 top N）只进 `mmda ops` 报告，**不作为构建断言**。

### 3.1 业务目标的可测指标（To Boss / To User，✔ 已裁 2026-09-24）

面向管理层与客户的四项指标，**定义与采集方式**如下（真源：[`vision.md`](vision.md) §6）：

| 指标 | 定义 | 采集方式 |
| --- | --- | --- |
| 生成覆盖率 | 产出物里可从模型生成、无需手写的行数占比 | 生成物中 `GENERATED` 区行数 / 总行数 |
| 变更成本 | 改一处模型 → 三端同步所需的**手工改动行数**与耗时 | 变更前后 diff 统计（越接近 0 越好） |
| 上手时间 | 业务人员经 AI 到「首个可用原型」的耗时 | 试点记录 |
| 模板复用率 | 跨项目复用的 module / 模板数占比 | 仓内统计 |

## 4. AI 时代的 review 分层

review 的目标从"人读代码"变成「**机器能判的机器判、AI 能证伪的 AI 证、人只做价值判断与签字**」。

| 层 | 执行者 | 查什么 | 产出 | 是否阻塞 |
| --- | --- | --- | --- | --- |
| **L0 机器 review** | `validate` / 静态质量检查 / 用例 | 语法语义、命名、引用、迁移合法性、权限矩阵、索引覆盖、孤儿用例、弱断言 | 诊断数组（`file:line:col`） | **必过** |
| **L1 AI review** | AI Reviewer | ① **一致性**：声明与实现是否一致 ② **遗漏**：需求空洞、未覆盖声明 ③ **风险**：破坏性变更的隐藏影响 ④ **反例**：构造能证伪当前设计的输入 ⑤ **风格**：与既有模型是否一致 | 报告 + 置信度 + **可复现证据** + 建议补丁 | **可验证的阻塞；不可验证的只提示** |
| **L2 人 review** | 按权限签字 | 价值取舍、业务语义、例外批准 | 签字 + 理由 | 按变更级别（[`workflows.md`](workflows.md) §8） |

**四条机制**（否则 AI review 会退化成噪音）：

1. **可验证率**：AI 提的每条意见必须附可复现证据（反例用例、diff 位置、声明冲突点）。统计**被采纳率**，低于阈值就降权并收敛提示范围——**用数据管 AI 意见的质量，而不是靠人忍着读**。
2. **AI 不得自我批准**（[`testing.md`](testing.md) §4.2-1 一致）：AI 只能提意见、给证据、出补丁。
3. **证据链进 changelog**：每次变更记录「谁 / 何时 / 依据哪些证据（校验结果、影响面、用例、AI 意见及采纳情况）/ 签了什么字」。事后可追溯，也让"当时为什么这么改"不再靠记忆。
4. **变更级别 × review 组合**（与 [`workflows.md`](workflows.md) §8 对齐）：L0 只跑 L0；L1 跑 L0+L1；L2 跑 L0+L1+L2（另一人签字）；L3 再加设计决策记录与外部评审。

**AI review 的三种高价值用法**（比"AI 帮我看看"具体得多）：

- **反向 review**：让 AI 扮演"实现者"，说出**它从模型里不得不自行假设的东西**——这些就是模型的漏洞（要么补声明，要么补文档）。
- **对抗 review**：AI 专门构造能推翻当前设计的反例，与 [`testing.md`](testing.md) §7 的变异测试互补（一个攻声明、一个攻实现）。
- **历史 review**：从缺陷库回溯同类缺陷模式，扫描**别处是否还存在同样的坑**（同类模式扫描），产出候选清单交人确认。

## 5. IDE 的全生命周期能力

一句话形态：**同一份真源，不同阶段的投影；追溯链不断。**

```
需求 REQ-x → 模型声明 → 用例 → 生成物 → 运行指标 → 缺陷 → 回归用例
   ↑                                                          │
   └────────────────── 回流（度量、索引建议、模型补丁提议）─────┘
```

**阶段口径（✔ 2026-09-25 作者裁定）**：开发阶段**只有四个**——**S1 意图 / S2 建模 / S3 验收 / S4 交付**（见 [`workflows-phase.md`](workflows-phase.md) §3）。下表是本文原来的八阶段切法**收敛到四阶段**后的对照：**架构 / 设计 / 编码合并为 S2 建模**（底座支撑下三者不严格可分）；**测试与验收合并为 S3 验收**；**运维在四阶段之外**（IDE 不提供运维能力，底座集成监控平台，其日志/报告发起新一轮迭代）；**演进 / 退役留在变更分级**。

| 阶段 | IDE 提供 | 证据物 | 门禁 | AI 角色 |
| --- | --- | --- | --- | --- |
| **S1 意图** | 需求条目化（`REQ-x`）、从纪要提炼候选需求、需求→模型追溯矩阵、**验收准则（UAT）编排** | 需求清单 + 追溯矩阵 + **可执行 UAT** | 每条需求有归属模块**且带可执行 UAT**（[`testing.md`](testing.md) §0.1） | 提炼 + 追问澄清 |
| **S2 建模** | 模块树、角色权限、跨模块流程、数据流、状态机与呈现编辑、图形与文本双向、capability 与**质量目标声明**（性能/安全/可靠性目标值）、**机械用例自动生成**、生成 + KEEP 区、三端切换 | 模块 / 角色 / 数据 / 行为 / 流程 / 呈现声明 + KEEP 实现 + 契约快照 | 无反向依赖、每 Action 有授权、目标值已声明、`validate` 零 error、**机械用例全绿** | 用例草稿 + 未覆盖清单 + 一致性检查 + KEEP 实现薄适配 |
| **S3 验收** | `test-gen` / `test` / `--impact` / `--mutate`、覆盖率看板、用例审阅面板、**用例库 / 集合 / 状态跟踪**（[`testing.md`](testing.md) §8.1 / §9.1）、**UAT 面**（§0.1：需求完成即出、必须可执行、hooks 驱动）、三层验收物 + **质量报告**（§3） | 用例 + 基线 + 覆盖率 + 变异存活 + **UAT 集合** + 验收单 + 质量报告 | 覆盖率门禁 + 变异阈值 + **UAT 集合全绿 + 验收单签字 + A/B 项达标** | 生成/自愈/诊断/回填（[`testing.md`](testing.md) §4.1）、报告生成、差异解释——**判定归人** |
| **S4 交付** | Profile 与交付配置、打包与镜像、`mmda doctor` 自检、**交付清单与版本**（**每轮迭代可追溯、可回滚**，[`workflows-phase.md`](workflows-phase.md) §3.5） | 交付包 + 镜像 + 版本 / 交付清单 | **基线四件套齐** + 交付包自检通过 + **上一轮可回滚** | 交付清单核对、变更说明生成 |
| **四阶段之外：运维**（**✔ 2026-09-25 作者**：运维严格说超出交付阶段，**IDE 不提供运维能力**） | **底座集成监控平台**（[`operations.md`](operations.md) 的标准出口：Prometheus / Zabbix / 夜莺）；IDE 侧只接收**运维日志与报告**并发起**新一轮迭代**；运行期回写对账（库 ↔ 文件漂移检测）也在这里 | 运维日志 / 报告 + 运行指标 + 对账报告 | **—**（不在 IDE 门禁内） | 漂移解释、补丁提议、调用方清单（→ 落成候选需求） |

**IDE 面板清单**（可直接当 P7 的验收项）：需求矩阵、模型编辑器（图形/文本双通道）、用例审阅面板、覆盖率看板、**质量雷达（九维）**、影响面面板、变更与签字记录、基线对比、运行期对账面板、退役扫描。 补（2026-09-25）：**测试资产面板** = 用例库 / 集合 / 状态（生命周期 + 执行两轴）/ 执行历史（[`testing.md`](testing.md) §8.1）；**UAT 面** = 需求完成即出、可执行、AI 经 hooks 驱动（同文 §0.1 / §0.2）。
