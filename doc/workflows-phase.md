## 0. 一句话立场

**阶段不是"工作量的分段"，而是"谁在什么条件下可以写下什么"。** 因此阶段数量由**写入者与冻结点**决定，不由产物类型决定——按产物类型切出来的阶段会随功能增长，按写入者切出来的阶段是稳定的。

## 1. 传统模型各自在解决什么，哪一条在 AI 时代失效

| 模型 | 它假设的瓶颈 | 核心机制 | AI 时代是否仍成立 |
| --- | --- | --- | --- |
| 瀑布 / V 模型（Royce、IEEE 12207、CMMI） | **实现**最贵 | 一次做对 + 重文档 + 重评审 + 阶段门禁 | ✗ 实现成本趋零；文档与图全是投影（[`PLAN.md`](../PLAN.md) §3.1/§3.2） |
| RUP / 螺旋 / 迭代 | 需求会变 | 分轮、风险驱动 | ✓ 仍成立，但轮次成本变低，**冻结点**成为主要成本 |
| 敏捷 / XP / Scrum / 持续交付（DORA） | 反馈要短 | 可工作软件优先、短迭代、自动化测试 | ✓ 但它只解决**实现侧**的反馈速度；意图澄清与验收仍靠人 |
| DevOps / SRE | 交付与运行要并入迭代 | 自动化流水线、可观测性、SLO | ✓ 全部保留（[`operations.md`](operations.md)） |
| **AI 时代（Spec-Driven / Vibe & Spec）** | **验证**最贵 | 声明即真源、机器生成、人只审声明与影响面 | ← **新增项**：瓶颈从「写出来」迁移到「说清楚 + 验对」 |

> 判据：一个传统阶段是否保留，看它**是否还承担唯一责任**。实现与文档已交给机器，测试已拆成"每站出口的机械验证 + 最后一站的人工验收"，所以它们不再独占一个阶段。

## 2. AI 带来的四条结构性改变

| # | 改变 | 本仓已裁口径（证据） | 对阶段模型的后果 |
| --- | --- | --- | --- |
| 1 | **实现不再稀缺，验证才是稀缺**——AI 能产出实现，也能产出"看起来对的实现与用例" | AI 断言必须双签；**变异存活率是最终裁判**（[`testing.md`](testing.md) §7）；用例从声明**机械生成**（同文 §3） | 「测试」降为**贯穿的验证腿**，只剩最后一站的人工验收（UAT） |
| 2 | **规格成为真源，消费者从"人"变成"人 + Agent"** | `.cursor/rules` + `conventions.md` 承载 AI 允许/禁止清单；[`ai/vibe-spec.md`](ai/vibe-spec.md) | 阶段产物的形态从**文档**变成**声明**（可解析、可 diff、可生成） |
| 3 | **文档、图、DDL、接口、元数据全部不再手写** | `mmda doc` / `mmda diagram` **只出不进**；DB 是产物/缓存 | **「文档阶段」消失**，文档与图并入每站的投影腿 |
| 4 | **人审的粒度从"读代码"变成"审声明 + 审影响面"** | `mmda diff --impact` 是人介入的触发点；三道闸（[`workflows.md`](workflows.md) §6.2） | 人只在**冻结点**与**破坏性变更**上介入，不逐行读产物 |

> 补充旁证（**未当场核，写进真源前需核原文**）：近两年公开研究（DORA 年度报告、METR 2025 的 RCT）都指向同一现象——个体产出变快，但交付吞吐与稳定性反而下降，原因是**验证与集成的成本没有随之下降**。这条若采纳，需带出处与版本写入。

## 3. 四站主干 + 三条贯穿腿

### 3.1 主干 = 人写什么（只有四站）

| # | 站 | 谁（帽子） | **人写什么** | 机器同时产出 | 这一站唯一的出口证据 |
| --- | --- | --- | --- | --- | --- |
| **0** | **意图** | 业务 + 架构师 | 需求条目 + 验收准则 | 用例、SRS、验收单骨架 | **需求基线**（每条可追溯） |
| **1** | **模型** | 架构师 + 设计师 | 模块 / 角色 / 数据 / 行为 / 流程 / 呈现 声明 | IR → 三端元数据、DDL、骨架、文档、图 | **契约快照 + 机械用例全绿** |
| **2** | **逻辑** | 程序员 + AI | KEEP 区实现（+ native 算法） | 骨架、薄适配 | **三端一致性用例全绿** |
| **3** | **交付** | 框架 + 运维 | Profile、交付配置 | 包、镜像、`mmda doctor`、验收单 | **基线全绿 + 验收单签字** |

### 3.2 三条贯穿腿（不是阶段）

| 腿 | 内容 | 为什么不是阶段 |
| --- | --- | --- |
| **验证腿** | 每站出口跑机械验证 → AI review 只做可证伪 → 人只签字 | 传统「测试阶段」被拆散：机械部分每站都有，人工部分只剩第 3 站的 UAT |
| **投影腿** | 文档 / 图 / DDL / 接口 / 元数据库 / 度量报告，全部单向产物 | 「文档阶段」消失：投影是每站的副产品，不是独立工作 |
| **运行腿** | 运维 → 度量回流 → 运行期回写对账 → 新需求（闭环回 0 站） | 运行不是"最后阶段"，是下一轮的输入（[`workflows.md`](workflows.md) §2 三个时间面） |

### 3.3 与传统切法的差值（差在哪，为什么差）

| 传统 | 本文 | 理由 |
| --- | --- | --- |
| 需求 / 设计 / 编码 / 测试 / 交付 | 0 / 1 / 2 / 3 | 站数一致，但**测试不再占一站**（降为验证腿），**原型生成不占一站**（是 1 站的自动动作） |
| 原型自动生成（`quickstart.md` §0 独列一段） | 并入 1 站出口 | 它是 `mmda generate` 的动作，不是人写东西的阶段 |
| 运维 / 退役（`quality.md` §5 八阶段里的两段） | 运行腿 + 演进 | 运维是回环的入口；退役是演进的一种变更（走变更分级，不另开阶段） |

## 6. 待补充（作者）

> 这一节留给你写。建议就下面几处落笔；其余仍可自由批注在正文行间。

1. **站的命名**：「意图 / 模型 / 逻辑 / 交付」是否合你的口径（例：0 站叫「需求」还是「意图」；2 站叫「逻辑」还是「实现」）。
2. **站的边界**：0 站与 1 站的交接点在哪儿？（是"需求条目确认"就算进 1 站，还是"模块树成形"才算）

4. **小项目/单人模式是否允许并站**（例如 0+1 站一次做完）——并站时门禁是否一项不减。
5. **AI 的介入点**：四条改变里哪几条你认可、哪几条要改写；第 2 条旁证要不要我去核原文后引用。
6. **退役/演进**：算运行腿的一个动作，还是需要独立站（`quality.md` §5 现有"演进 / 退役"一行）。

## 我的想法

1. AI的上下文有限制，遗忘会让人类很恼火

- 一旦事情复杂，经常反复，我就没有耐心了
- 明确的事情AI非常擅长，完成的很快，让我很开心
- 我以为我说得很清楚，AI也以为它理解了，实际是猜测了，导致问题扩散甚至方向偏离
- 想把一个复杂问题表达清楚很难，例如整个架构，至今我也不知道有没有范式、模式，就像软件的24设计模式

2. AI生成的测试不完全可靠

- 需要可测试性、确定性验证门控（hooks）

3. AI时代的阶段

- 需求阶段：解决Why & What，AI时代的意图（intent）和规格（spec），我没有严格区分这两个，因为你跟客户沟通的时候，难以分两个阶段说一个需求，你总是问他为什么要做，价值在哪里，然后要做成什么样，达到什么效果。是这个逻辑吧，哪怕你跟AI对话，除了专业的工程师，一般人不会知道先写一个intent.md，再写一个spec.md。

我们在这个阶段干嘛？输出*.mr，分三个层次：业务、用户、功能需求（能否对应我们的三级模块划分？），业务需求靠向intent，描述概况性的意图，业务意图存在层级结构，例如我们描述一级模块MES，你怎么描述呢？会说一些宏观的有哪些组成、目标是什么，通过下一级模块说清楚。二级模块，例如工厂模型：对工厂进行数字化建模，包括人、机、料、法（制程工艺路线）、环、测等，三级才是功能（Feature）

关键用户识别为role，包括组织架构、关键岗位、职责权限

业务流程

- 建模阶段：也是设计，解决

- 意图（解决Why），对应传统的需求规格（SRS）？出intent.md，
- 规划（解决What），出spec.md, 包括需求管理、模块分解、关键用户识别、USE-CASE
- 计划（plan解决How）
- 验证（hooks）

对比传统SDLC: plan-design-build-test-deploy-maintain
