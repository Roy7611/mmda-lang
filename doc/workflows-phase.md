# 开发阶段模型

> **这份文档解决什么**：把「MMDA 的开发分几个阶段」一次说清，并收敛三处现存口径——[`guide/quickstart.md`](guide/quickstart.md) §0（六段：需求→设计→原型→逻辑→测试→交付）、[`quality.md`](quality.md) §5（八阶段：需求→架构→设计→编码→测试→验收→运维→退役）、[`PLAN.md`](../PLAN.md)（里程碑 P0–P10）。
> **状态**：**草案 · 工作稿（2026-09-25 作者裁定四阶段主干 + 运维定位 + 迭代可追溯/回滚）**。四阶段口径已被引用于 [`requirements.md`](requirements.md) §2.2、[`testing.md`](testing.md) §0.1 / §0.2、[`project.md`](project.md) §1（四根目录）、[`quality.md`](quality.md) §5、[`guide/quickstart.md`](guide/quickstart.md) §0。
> **边界**：本文只谈**阶段**。扩展名统一（`*.m`）、目录自由与四根目录、JSON → M 语言格式是**下游决定**，住 [`project.md`](project.md) §1 / §11。

## 0. 一句话立场

**阶段由「回答什么问题 + 谁主导 + 出口证据」决定**，不由产物类型决定——按产物类型切（原型 / 文档 / 测试报告）会随功能增长而膨胀；按「问题 + 主导者 + 可验出口」切是稳定的。

**作者口径（2026-09-25，四阶段）**：

1. **意图**：解决 **why / what**，**这是人类参与最多的环节**。
2. **建模**：解决 **how**。**因为有了 MMDA 底座支撑，可能不需要严格区分架构、设计、开发**，因此模块分解、Actions、数据模型设计、状态机、数据流、UI 等等**只需要 modeling**。
3. **验收**：验收围绕测试、验证展开，是**质量把关**的环节，**完全交给 AI 难以达成**。
4. **交付**：交付物与部署（打包、版本、部署配置）。

**作者口径（2026-09-25 后半，运维的定位与迭代）**：

> 「**严格说，运维超出了交付阶段，但我们也不在 IDE 里提供什么运维能力，只是 MMDA 底座支持集成那些监控平台而已**。如果从 SDLC 的完整角度，**可以考虑根据运维日志和报告，发起新一轮迭代**。**IDE 在完成迭代后，新版交付，每一轮可追溯、回滚，即可**。」

由此三点定案：① **运维在四阶段之外**——IDE **不提供运维能力**，运维由**底座集成监控平台**（[`operations.md`](operations.md) 的标准出口：Prometheus / Zabbix / 夜莺）；② 四阶段**之外**还有一条**回流**：**运维日志与报告 → 新需求 → 新一轮迭代**；③ IDE 对交付职责的边界 = **「新版交付 + 每轮可追溯、可回滚」**（§3.5）。

## 1. 传统模型各自在解决什么，哪一条在 AI 时代失效

| 模型 | 它假设的瓶颈 | 核心机制 | AI 时代是否仍成立 |
| --- | --- | --- | --- |
| 瀑布 / V 模型（Royce、IEEE 12207、CMMI） | **实现**最贵 | 一次做对 + 重文档 + 重评审 + 阶段门禁 | ✗ 实现成本趋零；文档与图全是投影（[`PLAN.md`](../PLAN.md) §3.1/§3.2） |
| RUP / 螺旋 / 迭代 | 需求会变 | 分轮、风险驱动 | ✓ 仍成立，但轮次成本变低，**冻结点**成为主要成本 |
| 敏捷 / XP / Scrum / 持续交付（DORA） | 反馈要短 | 可工作软件优先、短迭代、自动化测试 | ✓ 但它只解决**实现侧**的反馈速度；意图澄清与验收判定仍靠人 |
| DevOps / SRE | 交付与运行要并入迭代 | 自动化流水线、可观测性、SLO | ✓ 全部保留，但**落在底座与运维平台侧**（IDE 不提供运维能力）；IDE 只保证**交付物可部署、每轮可回滚**（[`operations.md`](operations.md)、§3.5） |
| **AI 时代（Spec-Driven / Vibe & Spec）** | **验证**最贵 | 声明即真源、机器生成、人只审声明与影响面 | ← **新增项**：瓶颈从「写出来」迁移到「说清楚 + 验对」 |

> 判据：一个传统阶段是否保留，看它**是否还承担唯一责任**。实现与文档已交给机器 → 架构 / 设计 / 开发不再各占一站（合并为 S2）；**而验证与验收仍然只有人能拍板 → 它反而升为一站（S3）**。

## 2. AI 带来的四条结构性改变

| # | 改变 | 本仓已裁口径（证据） | 对阶段模型的后果 |
| --- | --- | --- | --- |
| 1 | **实现不再稀缺，验证才是稀缺**——AI 能产出实现，也能产出「看起来对的实现与用例」 | AI 断言必须双签；**变异存活率是最终裁判**（[`testing.md`](testing.md) §7）；用例从声明**机械生成**（同文 §3） | **验收成为独立阶段 S3**：机械部分散在每阶段出口，**人的判定集中在 S3**（[`testing.md`](testing.md) §0.1） |
| 2 | **规格成为真源，消费者从「人」变成「人 + Agent」** | `.cursor/rules` + `conventions.md` 承载 AI 允许/禁止清单；[`ai/vibe-spec.md`](ai/vibe-spec.md) | 阶段产物的形态从**文档**变成**声明**（可解析、可 diff、可生成）——这也是「一种后缀 `*.m`」的动机（[`project.md`](project.md) §1） |
| 3 | **文档、图、DDL、接口、元数据全部不再手写** | `mmda doc` / `mmda diagram` **只出不进**；DB 是产物/缓存 | **「文档阶段」消失**：文档与图并入**投影腿**（每阶段的副产品） |
| 4 | **人审的粒度从「读代码」变成「审声明 + 审影响面」** | `mmda diff --impact` 是人介入的触发点；三道闸（[`workflows.md`](workflows.md) §6.2） | 人只在**冻结点**与**破坏性变更**上介入，不逐行读产物 |

## 3. 四阶段主干 + 两条贯穿腿 + 每阶段出口门禁

### 3.1 主干 = 回答什么、谁主导、留下什么（只有四阶段）

| # | 阶段 | 回答什么 | 谁主导 | **人写什么** | 机器同时产出 | 这一阶段唯一的出口证据 | 默认根目录 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **S1** | **意图** | **why / what** | **业务 + 架构师（人类参与最多）** | 需求条目 + 验收准则（UAT） | 用例骨架、SRS、验收单骨架、候选模型差异 | **需求基线**（每条可追溯、且带可执行 UAT） | `intents/` |
| **S2** | **建模** | **how** | 架构师 + 设计师（AI 起草） | 模块分解 / Actions / 数据模型 / 状态机 / 数据流 / UI 声明 | IR → 三端元数据、DDL、骨架、文档、图 | **契约快照 + 机械用例全绿** | `models/` |
| **S3** | **验收** | **做好了没有** | **人定标准 + 审核；AI 跑与诊断** | 验收标准（UAT 用例）、阈值、判定口径 | 执行报告、覆盖率、变异存活、质量报告 | **UAT 集合全绿 + 验收单签字 + 质量报告** | `tests/` |
| **S4** | **交付** | **怎么上（这一版怎么交出去）** | 框架 + 交付负责人 | Profile / 交付配置 / 交付清单 | 包、镜像、`mmda doctor` 自检、**版本与交付清单** | **交付包（版本化）+ 自检通过 + 基线四件套齐** | `delivery/` |

> **S2 为什么不拆**：作者口径——「因为有了 MMDA 底座支撑，可能不需要严格区分架构、设计、开发」。底座把「架构 / 设计 / 开发」的产物统一成**同一种声明**（同一份 `.m`、同一套校验、同一份 IR），三者的区别退化为**同一阶段内的角色切换**（谁在写、谁签字），不再需要阶段门禁来分隔。
> **S3 为什么要独立**：作者口径——「完全交给 AI 难以达成」。机械验证可以零人工，但**验收标准定得对不对、这一版能不能交**，是需要人拍板的判定。
> **运维为什么不在四阶段内**：作者口径——「严格说，运维超出了交付阶段……我们也不在 IDE 里提供什么运维能力，只是 MMDA 底座支持集成那些监控平台而已」。所以：**IDE 的能力边界到交付为止**（交付物、版本、可回滚）；**运维是底座 + 监控平台的事**，它的产出（**运维日志与报告**）是**下一轮迭代的输入**（§3.2 / §3.5）。

### 3.2 两条贯穿腿（不是阶段）

| 腿 | 内容 | 为什么不是阶段 |
| --- | --- | --- |
| **投影腿** | 文档 / 图 / DDL / 接口 / 元数据库 / 度量报告，全部单向产物 | 「文档阶段」消失：投影是每阶段的副产品，不是独立工作（[`PLAN.md`](../PLAN.md) §3.1/§3.2） |
| **运维回流（在四阶段之外，不是腿也不是阶段）** | **底座集成监控平台** → **运维日志与报告** → 新需求条目 → 发起**新一轮迭代**（回到 S1） | 它不产生 IDE 侧的写入者，也不受 IDE 门禁约束；IDE 只做两件事：**交出版本化** + **把运维日志/报告落成候选需求**（[`workflows.md`](workflows.md) §2 三个时间面、§3.5） |

**每阶段出口门禁**（原「验证腿」的去处）：`mmda validate` / `mmda test` / `mmda snapshot` / `mmda diff --impact` 分布在**四个阶段的出口**，是**门禁**而不是一个阶段；机械部分零人工，人工判定集中在 S3。

### 3.3 与传统切法的差值（差在哪，为什么差）

| 传统 | 本文 | 理由 |
| --- | --- | --- |
| 需求 / 设计 / 编码 / 测试 / 交付 | **S1 / S2 / S2 / S3 / S4** | **架构 + 设计 + 编码合并为 S2 建模**（底座使三者不严格可分）；**测试独立为 S3 验收**（质量把关不能全交 AI） |
| 运维（`quality.md` §5 八阶段里的一段） | **四阶段之外**（底座集成监控平台；产出＝下一轮迭代的输入） | 作者口径：**运维严格说超出交付阶段，IDE 不提供运维能力** |
| 原型自动生成（`quickstart.md` §0 独列一段） | **S2 出口的自动动作** | 它是 `mmda generate`，不是人写东西的阶段 |
| 退役 / 演进 | **运行回流腿的一种变更**（走变更分级，不另开阶段） | 它不产生新的写入者，只产生新的一轮 |

| 上午稿（四站 + 三腿） | 作者四阶段 | 为什么改 |
| --- | --- | --- |

| 「1 模型 + 2 逻辑」分两站 | **合并为 S2 建模** | 底座支撑下**架构 / 设计 / 开发不必严格区分**，只需要 modeling |

### 3.5 迭代：每轮可追溯、可回滚（✔ 2026-09-25 作者）

> 作者口径：「**IDE 在完成迭代后，新版交付，每一轮可追溯、回滚，即可**」。

**一轮迭代 = 把 S1–S4 走完一次**，其产物是**四件套基线**（每一件都已存在现成机制，不需要新发明）：

| 阶段 | 本轮冻结的基线 | 现成机制 |
| --- | --- | --- |
| S1 意图 | **需求基线**（需求条目 + 可执行 UAT） | `requirements.md` §2.2；状态 `candidate → confirmed` |
| S2 建模 | **契约快照**（IR / 接口签名 / DDL / 渲染描述） | `mmda snapshot`（[`testing.md`](testing.md) §5-③） |
| S3 验收 | **用例基线**（`baseline/<版本>`，黄金用例集） | `mmda test --target …`；[`testing.md`](testing.md) §5 |
| S4 交付 | **交付包 + 版本**（含交付清单与校验和） | `mmda pack`；[`project.md`](project.md) §4 |

**可追溯 = 一条链不断**：`REQ-x → 声明点 → 用例 → 生成物 → 交付包版本`（运维日志/报告接在尾部，作为**下一轮的输入**而不是本轮的证据）。每一环都已有可机检的追溯机制（[`testing.md`](testing.md) §0-2 / §6、[`quality.md`](quality.md) §5 追溯链）。

**可回滚 = 切回上一轮的四件套组合**，而不是「git revert 一堆代码」：

| 回滚粒度 | 做法 | 代价 |
| --- | --- | --- |
| **整体回滚**（推荐默认） | 把上一轮的**交付包版本**重新发布（生成物都是派生物，不需要回退源码树） | 低 |
| **阶段内回退** | 回到上一轮的需求基线 / 契约快照 / 用例基线中的某一件，然后**重新投影**（重新生成 + 重跑用例） | 中（要过一遍该阶段门禁） |
| **单个变更回退** | 走**变更分级**（[`workflows.md`](workflows.md) §8）反向变更，仍留痕 | 低 |

> 判据一句话：**回滚的对象是「基线组合」，不是「代码差异」**——因为代码、DDL、文档、图全是声明投影出来的产物，切回基线 + 重跑投影即可复现上一版。

**这条口径的待裁**（见 §6 开放项 6/7）：迭代编号形态、回滚粒度默认值。

| 6 | **迭代编号形态**：`I1` / `I2`，还是复用 `changelog/` 的 `seq` / 交付包版本号；迭代号与需求基线、用例基线、交付包版本的对应关系 | 建议**复用交付包版本号作为迭代号**（一轮迭代 = 一个交付包版本），需求/用例基线各带同一迭代号；不再新造 `I*` 编号 |
