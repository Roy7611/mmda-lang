## MMDA 随想录

如何让业务人员能够建立系统？还是让技术工程师快速构建系统？业务和IT是有沟通鸿沟的存在，因此才有系统分析师的价值，软件工程方法中需求过程往往很不容易，一方面业务人员口述或笔述的需求常常不完整、没想好，另一方面IT人员不懂业务，理解不准确、会遗漏，加上沟通过程信息损耗，很容易导致需求偏差。因此需求过程注定需要多次、反复迭代，是一个耗费时间、人力、成本的复杂过程。

除非你是跨专业的复合型人才，既有业务实践经验，又具备高水平的IT专业水准，把这个沟通成本节约了。要不然，系统分析师得遵循软件需求工程的方法论，从业务需求、用户需求和（非）功能需求三个层面，经过访谈、资料收集来弄清现状，包括组织、流程、数据和报表输出等。然后撰写《软件需求规格书》（SRS，Software Requirements Specification），其中你会使用图文来描述软件需求，例如一个个UML用例图（USE-CASE）、数据流图等。评价软件需求过程的标准是：清楚(Clear)、完整(Complete)、一致(Consistent)、可测试(Testable)，此外还有其他的概念，如可跟踪的、可修改的等等。

### 有没有更好的方法？先异想天开一下。

**系统模块分解**，即 SERU 需求方法论中的 `S`，使用系统逻辑架构图、层级菜单。

**数据结构建模**：

1. **组织架构建模**，图形化输入组织架构图、岗位矩阵图，导入职员清单。前面两个可以通过最佳实践、标杆模板来加快建模过程。
2. **业务对象建模**，元数据编辑，针对模块小范围定义局部数据模型（ER 图）。
3. **业务主题建模**，为 BI 提供数据源。枚举可定义为维度，生成固定维度模型。
4. **给模块设置数据模型**，首页过滤器、展现器（Index、Report、Dashboard、CRUD）等。

**业务流程建模**：

1. **图形化输入 BPMN 表示的流程图**，选择输入数据源，数据转换器、映射，事件、任务节点，以及输出。
2. **节点任务、事件都生成代码**，这部分由技术人员实现，插件式加载。
3. **角色由岗位生成**，添加。
4. **给模块设置流程**，Action 串联不同模块间的数据流（DFD）。
5. **给模块数据模型设置状态机**，自动执行流程对模型状态的更改。

**UI 设计**（<https://github.com/material-foundation/material-color-utilities>）：

1. **配色方案**，采用 Material Design，支持 Theme Builder。ColorRole 用于可视化建模的基础。
2. **Field Set 对 Field 进行分组**，根据数据类型自动生成默认的呈现器和编辑器。

**数据可视化**：

1. **自定义报表工具**，定义数据源、关联关系，过滤参数和查询条件，结果展现方式等。
2. **BI 看板设计工具**，看板布局、KPI 数据资产、底层采用 ClickHouse 存储，学习 Power BI / Tableau。

通过以上的过程，即可构建生成源码、自动编译、打包发布（结合 DevOps）。

每次修改应自动记录变更轨迹，结合源码管理工具实现版本控制，使得可以回滚设计。因此设计得使用文件存储，设计工具开发为 VS Code 插件或者 IDEA 的插件。

**绘图工具**：ER、数据、流程、表单、BI、脚本、代码生成。
