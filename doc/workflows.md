# 角色与工作流（Roles & Workflows）

> **这份文档补什么**：`ide/workflow.md` 是**工具视角**（Architect UI 的六步导航），`ai/tools.md` 是**工具面**（MCP 工具清单），`ai/vibe-spec.md` 是**协作模式**（Spec → Vibe）。
> 三者都只覆盖了「架构师 + AI」。本文补的是**角色视角**：五类用户各自的输入、产物、写入边界、交接物、验收门禁，以及他们**在同一份真源上怎么不打架**。
> 状态：草案（2026-09-24）· 与 [`targets.md`](targets.md) 的 capability、[`protection.md`](protection.md) 的算法边界联动。

---

## 0. 四条共同前提（所有职责与模式共享）

1. **唯一真源 = `.mmda` 项目目录**（文件形态，进 git/svn，一对象一文件）→ 谁改了什么，diff 说得清。
2. **生成区 / KEEP 区分离**：`generated/**` 里的 `GENERATED PARTS` 区由工具写、**任何人不得手改**（沿袭 `mmda-factory` 的 `~GENERATED/~KEEP` 协议）；业务逻辑只写 KEEP 路径（由 `conventions.md` 指定）。
3. **所有写入必须过 `mmda validate`**，语义错误不许进真源；**所有结构性变更必须留 `changelog/NNNNNN.json`**。
4. **IR 是产物不是真源**：元数据库、DDL、代码、图形投影 `*.g`、i18n 导出物都是 IR 的下游，改它们等于改缓存（见 `PLAN.md` §3.1/§3.2）。

## 1. 五类职责与写入边界

**这五类不是岗位，是职责（帽子）。** 同一个人可以同时是业务专家 + 设计师 + 程序员，从需求一路做到交付；关键不是「他是谁」，而是「这次变更要满足什么条件」。

帽子只有一个实际用途：**决定谁承担后果**（对生产数据、对客户承诺）。因此帽子决定**签字**，不决定「能不能写」。

| 职责（帽子） | 关心什么 | 主要产物 | 不碰什么 |
| --- | --- | --- | --- |
| **架构师** | 边界、职责、依赖方向、角色权限、交付形态 | 模块树、角色/权限、跨模块流程、Codegen Profile、capability 声明 | 字段级细节、KEEP 区实现 |
| **软件设计师** | 领域模型与交互 | Record / Enum / STM / Converter / 定制视图 / i18n 词条 | 模块边界、构建与部署、KEEP 区实现 |
| **程序员** | 让系统真的跑起来 | KEEP 区实现、Logic 钩子、事件订阅、native 算法 crate、迁移脚本、测试 | 生成区、模型语义（要改就回真源改） |
| **AI Agent** | 在约束内补全与批量作业 | 元模型补丁（提议态）、生成物、测试用例、影响面报告 | 生成区手改、破坏性变更（需人批准）、未声明的字段 |
| **业务人员**（通过 AI） | 业务语义对不对 | 中文标签/枚举成员/必填与取值范围/页面字段顺序的**确认意见** | 一切技术实现与文件写入 |

### 1.1 三种工作模式（门禁不可裁剪，只裁剪签字人数）

| 模式 | 典型形态 | 签字要求 | 不可裁剪的门禁 | AI 的角色 |
| --- | --- | --- | --- | --- |
| **单人模式** | 一人到底：业务专家 + 技术全包 | 允许 **self-approve**；L2/L3 用「**AI 对抗复核 + 冷却期 + 回滚演练**」替代第二个人的眼睛 | `validate` / `diff --impact` / changelog / 生成回归 / 三端一致性（若启用） | **第二双眼睛的替代者**：出影响面、反例用例、迁移 dry-run，并明确写「这个改动可能怎么出错」 |
| **结对模式** | 设计 + 实现分两人 | L1 一人签字；**L2/L3 必须另一人签字**（不可同一人） | 同上 | 出报告与用例，**不签字** |
| **团队模式** | 五顶帽子分多人 / 跨组织 | 按 §1.3 矩阵指派签字人；L3 另需设计决策记录（`docs/adr/`） | 同上 + 评审记录 | 出报告、跑门禁、开 PR |

**为什么只裁剪签字人数**：质量和合规靠的是**证据**（校验结果、影响面、changelog、测试、回滚路径），不是靠人数。人少时证据一项都不能少，只是把「第二双眼睛」替换成 **AI 对抗复核 + 时间冷却 + 可回滚验证**。

### 1.2 权限在项目管理里配置，导航与边界按角色权限限制

**已裁（2026-09-24）**：**模式与权限在 IDE 的「项目管理」里配置**——项目选一个 `mode`（单人 / 结对 / 团队），并按账号分配角色。

| 配置项 | 作用位置 |
| --- | --- |
| `mode` | 决定签字人数（§1.1）与是否允许多视图切换 |
| 账号 → 角色 | 决定**导航**（没这顶帽子就看不到对应导航项/编辑区）与**写入边界**（§1.3 矩阵是工具强制的硬边界，不只是约定） |
| 角色 → 签字权 | 决定 §8 各变更级别的签字落到谁 |

> 注意：这里配置的是「**账号 → Role 的授予**」。**Role 本身是设计元素**——需求阶段识别的关键用户，声明在语言里（`flow/roles/*.mr`，与 `biz/*.ma` 的模块分解**同级**，见 [`meta-model.md`](meta-model.md) §8.1）；Role 的能力范围（`auth module` / `actions` / `scope`）由架构师设计，**谁持有它**才是在 IDE 里配置的。

**因此「一人到底」不是绕过权限模型，而是把多项角色授予同一个人**：规则不变、门禁不减；同一个账号同时持有几顶帽子时，IDE 要在界面上明确提示「你现在在改哪一层、这一层改完必须跑什么」。

### 1.3 写入权限矩阵（三种模式通用）

**读法**：每一行不回答「谁可以写」，而回答「**这类文件被改动时必须满足什么条件**」——同一人可以同时满足多行（他就是那几顶帽子）。矩阵里的签字人按 §1.1 的模式落到具体人身上。

`写` = 可直接提交；`提议` = 出补丁/PR 由他人批准（单人模式下由 AI 对抗复核替代）；`审` = 只确认语义；`禁` = 不许动。

| 对象 / 文件 | 架构师 | 设计师 | 程序员 | AI Agent | 业务人员 |
| --- | --- | --- | --- | --- | --- |
| `biz/*.ma`（模块树、模块依赖） | **写** | 读 | 读 | 提议 | 读（中文视图） |
| `flow/roles/*.mr`（角色、权限、数据范围） | **写** | 读 | 读 | 提议 | 审 |
| `data/models/*.mm`、`data/enums/*.me` | 审 | **写** | 读 | 提议 | 审（标签/取值） |
| `data/stms/*.ms`（状态机、Action） | 审 | **写** | 读 | 提议 | 审（状态名/流转语义） |
| `flow/converters/*.mc`、`flow/*.mf`、`flow/*.mb` | **写** | **写** | 读 | 提议 | 审 |
| `ui/**/*.mi`（五视图定制） | 读 | **写** | 读 | 提议 | 审（字段顺序/标签）——**消费方唯一 = mmda-vue**（[`presentation.md`](presentation.md) §5.1）；前端 kit（Vue `vui*` / React `rui*`）**由开发者自选**（写自定义前端 UI 插件时按熟悉度挑） |
| `conventions.md`、`codegen/profiles/*.yaml`、capability 声明 | **写** | 读 | 写（工程参数） | 提议 | — |
| `generated/**` 的 GENERATED 区 | 禁 | 禁 | 禁（工具写） | 工具写 | — |
| KEEP 区 / `handlers/**`（业务逻辑） | 禁 | 禁 | **写** | **写**（受 `conventions.md` 约束） | — |
| Rust 算法 crate（独立仓，见 `protection.md`） | 审 | 读（契约） | **写** | 写 | — |
| `changelog/NNNNNN.json` | — | — | — | — | — |
| ↑ 由**工具自动追加**，任何角色都不手写 | | | | | |
| 元数据库 / DDL / 代码 / `*.g` / i18n 导出 | 只读 | 只读 | 只读 | 只读 | 只读 |

## 2. 三个时间面与各自的 owner

| 时间面 | 数据流 | owner | 门禁 |
| --- | --- | --- | --- |
| **设计期** | 人 → `.mmda` 文件 → IR | 架构师 / 设计师（人写），AI 提议 | `mmda validate` 零 error；一对象一文件；有 changelog |
| **构建期** | IR → 元数据库 / DDL / 代码 / 文档 / `*.g` | 工具（`mmda generate`），程序员维护 Profile | 生成物与真源一致（checksum）；KEEP 区未被覆盖（回归用例） |
| **运行期** | 库 → 回写 `.mmda` → 进版本控制 | 运维修配置的人提交，架构师/设计师复核 | `mmda import --db` 逐对象对账 + diff 预览；未经回写的库改动视为漂移 |

> 第三条是 A4/B2 的落地：**库允许改，但必须回到文件**（`PLAN.md` §3.2）。运行期改配置的人不新增职责，就是「戴设计师/架构师帽子的人站在运维现场」；他改完同样要回写文件并留 changelog。**位置变了不代表规则变了。**

## 3. 架构师工作流（7 步）

| # | 输入 | 动作 | 产物 | 工具 | 门禁 |
| --- | --- | --- | --- | --- | --- |
| 1 | 业务需求（口述/文档/会议纪要） | 划子系统与模块边界；定模块编码 | `biz/*.ma` 模块树 | Architect UI 导航树 / M语言 | 每个 Feature 有归属模块；无空模块 |
| 2 | 模块树 | 定**数据所有权**（哪个模块拥有哪个 Record，跨模块只走声明引用） | 模块 → Record 绑定 | 菜单树编辑 | 无反向依赖；无「两个模块都改同一张表」 |
| 3 | 数据所有权 | 定领域硬约束（主键策略、租户键、编号规则、审计字段） | 项目级约定 + `conventions.md` 骨架 | M语言 / 模板 | 约定可被 `mmda validate` 检查 |
| 4 | 领域硬约束 | 定角色与权限（role / auth / scope：OWNER/WORKGROUP/DEPARTMENT/ALL） | `flow/roles/*.mr` | 角色权限编辑器 | 每个 Action 有授权角色；数据范围字段齐（`creatorId`/`ownerId`） |
| 5 | 角色权限 | 定跨模块流程与数据流（BPMN 池/活动/网关、Converter 映射） | `flow/*.mb`、`flow/*.mf`、`flow/converters/*.mc` | BPMN 图 / DFD | 每条流有触发者与结果事件；无孤立节点 |
| 6 | 全部模型 | 定**交付形态**：目标端、capability、算法保护档 | capability 声明（含 `algorithm(...)`） | M语言 / CLI | 语言用到的能力在目标端都有声明（否则生成期报错） |
| 7 | 完成的设计 | 出 Codegen Profile、跑一次全量校验与生成、评审 | `codegen/profiles/*.yaml` + 评审记录 | `mmda validate` / `generate` | 零 error；生成成功；**Spec 完成度清单**（`ai/vibe-spec.md` §5）全绿；**架构评估**硬规则无新增违规（[`architecture-review.md`](architecture-review.md) §5） |

**交接物**：模块树 + 角色权限 + capability 声明 + `conventions.md` + 一次成功生成。→ 交给**设计师**做字段级设计与**程序员**搭骨架。

## 4. 软件设计师工作流（8 步）

| # | 输入 | 动作 | 产物 | 门禁 |
| --- | --- | --- | --- | --- |
| 1 | 模块树 + 数据所有权 | 建 Record 骨架（名称、主键、租户键、审计字段） | `data/models/{schema}/{Name}.mm` | 命名与 `conventions.md` 一致；一对象一文件 |
| 2 | Record 骨架 | 加字段：类型/长度/可空/默认值/@{注解}（`@Ref`/`@One`/`@Many`/`@Id`/`@Index`/`@PartitionID`） | 同上 | 引用目标存在；类型与长度合法；无裸字符串表达式 |
| 3 | 字段 | 写业务约束与计算属性（`@Computed`、约束表达式） | 同上 | **表达式纯函数**（禁 IO/赋值/随机/时间依赖，`doc/events.md:97-102`） |
| 4 | 状态型实体 | 建 `@State` 枚举 + STM：`stm X on R.field { action … { transition A->B } }` | `data/enums/*.me`、`data/stms/*.ms` | 每个 `@State` 字段有 STM；无不可达状态；每个 Action 有前置状态 |
| 5 | 跨对象编排 | 定 Converter（数据流）与跨模块流程节点 | `flow/converters/*.mc`、`flow/*.mf`、`flow/*.mb` | 映射字段类型兼容；流程节点有 owner |
| 6 | 模型 | 设计呈现：五视图引用、UiField（editor/formatter/align/placeholder）、分组 `groupLabel` | `ui/**/*.mi` → `MetaUi` | 未提供 `.mi` 时框架能按元数据生成标准 CRUD；**渲染方唯一 = mmda-vue**（[`presentation.md`](presentation.md) §5.1），后端只产 `MetaUi` |
| 7 | 呈现 | 填 i18n：displayLabel、字段 placeholder/tooltip、枚举成员标签（默认语言 + 其余语言） | 模型内 i18n 词条 | 无空标签；**多语言映射编辑**并排核对（`presentation.md` §7） |
| 8 | 完成设计 | 出 E-R 图 / 状态图并自检、跑校验 | `*.g` 图形投影 + 校验报告 | `mmda validate` 零 error；图形与文本双向一致 |

**交接物**：可生成的完整元模型（模型 + 状态机 + 呈现 + 词条）。→ 交给**程序员**实现逻辑，交给**业务人员**审语义。

## 5. 程序员工作流（6 步）

| # | 输入 | 动作 | 产物 | 门禁 |
| --- | --- | --- | --- | --- |
| 1 | 完成的元模型 | 按 Profile 生成骨架（Java / C# / TS 三端或按需） | `generated/**` | 生成成功；KEEP 区回归用例通过（旧手写代码未被覆盖） |
| 2 | 生成的骨架 | 在 **KEEP 区**实现 Logic 钩子与 Action Handler：校验前置状态、事务边界、幂等 | `handlers/**`、KEEP 区 | 不违反 `statusTransition` 前置状态；不改生成区 |
| 3 | 事件声明 | 实现事件订阅（C# 侧 `IEventBus` 已有；Java 侧按 `PLAN.md` §3.7 契约补齐） | 订阅实现 + 投递幂等 | 投递语义与 `events.md` 一致；有重放/幂等测试 |
| 4 | 算法契约（`algorithm(...)`） | 在**独立 Rust 仓**实现算法 crate（`cdylib` + 加固，见 `protection.md` §6）；写薄适配 | 算法 crate + `XxxNative.java/.cs` | 算法体不进交付仓；`nm -D` 只见少量 C ABI 符号；许可校验生效 |
| 5 | 模型变更需求 | **回真源改**（`.mmda`），重跑生成；需要时写迁移脚本（破坏性变更） | 模型补丁 + 迁移脚本 | 破坏性变更须架构师批准 + 变更分级（§8） |
| 6 | 全部实现 | 集成测试 + 一致性测试 | `tests/**` | `mmda test --target java,csharp,ts` 三端结果一致（P9） |

**红线**：任何「先改生成代码、再想着回写模型」的做法一律退回——那正是漂移的来源。

## 6. AI Agent 工作流协议（最需要细化的一环）

### 6.1 会话前置（每次任务开头固定动作）

1. `mmda_project_open` → 拿 manifest 摘要与项目约定版本；
2. `mmda_get_conventions` → 读 KEEP 路径、命名、禁止项；
3. `mmda_get_record` / `mmda_list_modules` → 只读**相关子集**，禁止整仓灌进上下文；
4. 明确本次任务的**变更级别**（§8）与**影响面**（先读后写）。

### 6.2 三道闸（缺一不许提交）

```
① mmda validate            → 语法/语义必须零 error（含新引入的 warning 说明）
② mmda diff --impact       → 影响面清单：哪些 Record/字段/接口/页面/DDL 会变
③ 签字                     → 按 §1.3 矩阵落到具体人；模式决定人数（§1.1）：
                             单人模式可 self-approve（L2/L3 另需 §8 的 AI 对抗复核 + 冷却期 + 回滚演练）
                             结对/团队模式由另一人签（L2/L3 不可同一人）
```

### 6.3 允许 / 禁止清单（同时写进 `.cursor/rules` 与 `conventions.md`）

| 允许 | 禁止 |
| --- | --- |
| 在受约束范围内新增/修改元模型片段（走 `dryRun` → 确认 → 提交） | 手改 `generated/**` 的 GENERATED 区 |
| 在 KEEP 路径实现 Action/Handler/订阅 | 绕过 `validate` 提交；跳过 changelog |
| 生成代码、生成测试用例、出影响面报告 | 未经批准做破坏性变更（删/改名/改类型/改必填） |
| 批量补齐（如给 N 个对象加同一个标准字段）**且**附清单与 changelog | 批量重命名公共标识符、批量改 `@Ref` 目标 |
| 提出重构建议（写成 PR，不直接落盘） | 把密钥/连接串写进 `.mmda` 或生成物 |

### 6.4 一次变更的固定动作序列

```
open → read(相关子集) → dryRun 补丁 → validate → diff --impact
     → 人工批准 → 落盘（含 changelog）→ generate → 跑测试 → 开 PR（描述里附影响面与变更级别）
```

### 6.5 失败与回滚

- `validate` 失败：**只回退本次改动**，不要「顺手修别的」；
- 生成后发现 KEEP 区被覆盖：立刻回滚生成物提交（KEEP 区是手写资产）；
- 影响面超预期（例如波及 > 5 个 Record 或任何破坏性项）：停下来出报告，等人决策。

### 6.6 批量作业的额外要求

覆盖 ≥ 3 个对象、或涉及任何破坏性变更时：必须**先出清单**（对象 + 字段 + 前后对比）、**分级**（§8）、**经人批准**，并逐对象写 changelog 条目。批量作业不允许「一把梭 + 事后解释」。

### 6.7 与 MCP 工具面的对应

`ai/tools.md` 的工具清单即本协议的执行面：读 → `mmda_list_records`/`mmda_get_record`/`mmda_list_modules`；写 → `mmda_patch_record`/`mmda_add_field`/`mmda_add_action`（均支持 `dryRun`）；校验 → `mmda_project_validate`；生成 → `mmda_generate`。新增 `mmda diff --impact` 与 `mmda test --target …` 两个工具面（`PLAN.md` §3.3 的 `mmda-test`）。

## 7. 业务人员路径（通过 AI，不碰文件）

**他能决定的**：业务语义 —— 中文标签与叫法、枚举成员是否齐全、哪些字段必填、取值范围是否合理、页面上字段的顺序与分组、报表要看什么。
**他不能决定的**：字段类型/长度、索引与分区、状态机怎么切、权限模型、任何技术实现。

| # | 动作 | AI 产出 | 谁批准 |
| --- | --- | --- | --- |
| 1 | 口述业务需求（用业务词，不用技术词） | 复述理解 + 澄清问题清单 | 业务人员确认理解无误 |
| 2 | 确认后 | **候选元模型差异**（新增/修改哪些 Record/字段/枚举/页面），用业务语言描述 | — |
| 3 | AI 追加提示 | **业务影响面**：涉及表结构变更时明确说「会影响历史数据，需要迁移」；涉及权限时说「谁会看到/能改」 | 业务人员确认语义 |
| 4 | — | 落成**提议态补丁**（PR） | **设计师**（模型语义）/ **架构师**（边界、权限、破坏性） |
| 5 | 批准后 | 合并 + changelog + 生成；业务人员收到**中文变更回执**（这次改了什么、什么时候上线） | — |

**三条红线**：① 业务人员不直接改真源，只审语义；② 破坏性变更必须架构师批准（不能只经业务人员同意）；③ 业务人员不参与技术选型讨论——AI 要把技术选项**翻译成业务后果**再问他。

**UAT 反馈回路**：使用中发现的问题 → issue → 分三类路由：**语义错**（业务人员 → 设计师改模型）、**交互不顺**（业务人员 → 设计师改 `ui/**/*.mi`）、**性能/缺陷**（→ 程序员改 KEEP 区/native 算法）。

## 8. 变更分级（决定要留什么证据、要谁签字）

| 级别 | 例子 | 必须留下的证据 | 签字要求（单人模式） | 签字要求（结对 / 团队） |
| --- | --- | --- | --- | --- |
| **L0 无副作用** | 注释、文档、`*.g` 布局 | 工具校验结果 | 无需签字 | 无需签字 |
| **L1 非破坏** | 加可选字段、加枚举成员、加 Action/STM 状态、加 `ui/**/*.mi`、加别名 | `validate` 零 error + 影响面报告 | self-approve | 1 人签字（设计师或架构师） |
| **L2 破坏** | 删字段/删表、改名、改类型/长度、必填化、删枚举成员、改 `@Ref` 目标 | 迁移脚本 + 兼容期策略（双写/灰度/回填）+ 在副本库上的迁移演练结果 + **回滚路径** + 三端一致性测试 | **AI 对抗复核**（写明最坏情况与反例）+ **冷却期**（候选分支挂起 ≥ 24h + 自动对账）+ **回滚演练通过** | **另一人签字**（不可同一人）+ 上述全部证据 |
| **L3 结构性** | 模块边界调整、权限模型变更、capability/目标端变更、算法服务化 | 设计决策记录（`docs/adr/`）+ 受影响角色交接物重出 + L2 的证据（若含破坏项） | 同 L2 + ADR；**建议**找一位外部/同侪评审（可异步，不必同组织） | 架构师签字 + ADR + 评审记录 |

> 分级的用途：让 AI 与人**在同一套规则下判断**「这个改动要不要停下来、要留什么证据」。判据不进文档就必然退化成口头约定。
> 单人模式的意义在于：**门禁一项不减，只是用「AI 对抗复核 + 时间冷却 + 回滚验证」把第二个人的作用拆解成可自动化的步骤**。这三样都能被工具跑（`mmda diff --impact`、候选分支对账、迁移 dry-run），所以一人到底不需要靠自觉。

**review 分层**（决定每个级别要过哪几层评审）：

| 层 | 谁 | 阻塞性 |
| --- | --- | --- |
| **L0 机器** | `validate` / 静态质量检查 / 用例 | 必过 |
| **L1 AI** | AI Reviewer（一致性 / 遗漏 / 风险 / 反例 / 风格） | **可验证的阻塞，不可验证的只提示**；附可复现证据，并统计采纳率 |
| **L2 人** | 按 §1.3 权限签字 | 按级别（L0 免、L1 一人、L2/L3 见上表） |

细则见 [`quality.md`](quality.md) §4（含 AI review 的可验证率机制与三种高价值用法）。

## 9. 交接协议（Handoff）

| 上一步的产物 | 接手方 | 接手前的验收（可执行） |
| --- | --- | --- |
| 模块树 + 数据所有权 + `conventions.md` | 设计师 | `mmda validate` 零 error；模块与 Record 绑定完整 |
| 模型 + 状态机 + 呈现 + 词条 | 程序员 | 生成成功；五视图可渲染；状态机无不可达状态 |
| 生成骨架 + Profile | 程序员 | KEEP 区回归用例通过 |
| KEEP 区实现 + 迁移脚本 | 测试/交付 | `mmda test --target java,csharp,ts` 一致；迁移脚本在副本库上跑通 |
| **用例与基线**（机械生成 + AI 生成人审） | 交付 / 业务人员 | 跑基线全绿；覆盖率（字段/迁移/权限/能力 100%）达标；中文验收单已签字（[`testing.md`](testing.md) §5） |
| 候选模型差异 + 业务影响面 | 业务人员 | 影响面用业务语言写清（涉及谁、看得到什么、历史数据怎么办） |
| 提议态补丁（PR） | 架构师/设计师 | 变更级别已标注；changelog 条目已附 |
