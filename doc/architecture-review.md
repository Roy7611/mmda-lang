# 架构评估（Architecture Review）

> **这份文档要解决什么**：验收不能只验"功能对不对"，还得**验架构设计本身好不好**——分层、分模块、SOLID、耦合内聚、数据所有权。
> MMDA 在这里有个天然优势：**架构是声明的**（模块树、数据所有权、角色权限、跨模块流程、capability 都在 `.mmda` 里），所以这些标准**大部分能在设计期静态算出来**，不用等代码。
> 状态：草案（2026-09-24）· 与 [`quality.md`](quality.md)（质量模型）、[`workflows.md`](workflows.md)（职责与变更分级）、[`contracts-inventory.md`](contracts-inventory.md)（现状盘点）联动。

---

## 0. 三条原则

1. **评估的可信度来自「规则可判定 + 证据可指」**：每条结论给规则号、`file:line`、改法。**总分只用于趋势，门禁只看违规清单**（总分会让违规互相掩盖，20 个严重违规 + 100 个合规项照样能凑出高分）。
2. **设计期就能跑，且与代码无关**：架构声明的存在使 ARCH-1xx/2xx/3xx 全部是静态规则。等代码写出来再评架构，代价已经付完了。
3. **评审的产出必须包含改法**：只报"耦合偏高"的评审等于没做。建议要写成动作（拆哪个、提哪个接口、迁哪些字段）+ 影响面 + 变更级别。

---

## 1. 评估的输入与视角（ISO/IEC/IEEE 42010 落地）

42010 的框架是「**利益相关者 → 关注点（concern）→ 视角（viewpoint）→ 视图（view）**」。映射到 MMDA：

| 关注点（谁关心） | 视角 / 视图 | 承载文件 | 可自动检查 |
| --- | --- | --- | --- |
| 边界与依赖（架构师） | 模块树 + 依赖图 | `biz/*.ma` | ARCH-101/102/106 |
| 数据所有权（架构师、DBA） | E-R 图 + 模块-对象绑定 | `biz/*.ma`、`data/models/**` | ARCH-104/105 |
| 领域模型（设计师） | 记录模型 / 枚举 / 状态机 | `data/**` | ARCH-203/204/401 |
| 数据流（设计师） | DFD / 节点图 / 数据映射图 | `flow/*.mf`（+ `*.mf.g`；跨模块流程另在 `flow/*.mb`） | ARCH-103/105 |
| 权限与安全（架构师、审计） | 角色权限视图（**Role 与 Module 分解同级**，见 [`meta-model.md`](meta-model.md) §8.1） | `flow/roles/*.mr` | ARCH-304 |
| 扩展与租户（架构师） | include / 扩展文件 | 项目清单 + `{tenant}/` 文件 | ARCH-302 |
| 交付与目标端（架构师） | capability / Profile | Profile + capability 声明 | ARCH-305 |
| 变更与演进（架构师、运维） | 变更日志 + 影响面 | `changelog/*.json` | ARCH-501/502 |

**42010 给的第一份交付物**：**关注点 × 视角的缺口清单**——哪个关注点没有视角承载、哪个视角没有文件承载，这本身就是评审结论（`mmda arch report` 首节输出）。

## 2. 规则集（可判定为主，编号 ARCH-1xx/2xx/3xx/4xx/5xx）

**等级沿用 [`quality.md`](quality.md) §2**：A 设计期静态 / B 生成后可判定 / C 运行期 / D 人评。首版门禁范围见 §5。

### 2.1 分层与依赖（硬规则）

| 规则 | 内容 | 等级 |
| --- | --- | --- |
| **ARCH-101** | 依赖单向：UI → Logic → Data，**禁止反向依赖** | A |
| **ARCH-102** | **禁止循环依赖**（模块级与对象级都要查；对象级用 `@Ref`/`@One`/`@Many` + Converter 构成的有向图） | A |
| **ARCH-103** | 禁止跨层跳过（UI 直接引用 Data 层对象），除非登记在白名单并写理由 —— **UI 层 = mmda-vue 前端项目**（[`presentation.md`](presentation.md) §5.1），故"UI 层"指 `packages/core` 的 metaui/ui 消费面 | A |
| **ARCH-104** | **数据所有权唯一**：一个 Record 只被一个模块写 | A |
| **ARCH-105** | 跨模块只走声明接口（不得直接改别人拥有的对象；引用必须走 `@Ref` 声明 + 权限） | A |
| **ARCH-106** | 无孤立模块、无未归属 Feature；模块树无空壳 | A |
| **ARCH-111** | **对外可见的 Record 必须有唯一 owner module**（无归属即不可外露——权限按 module 授予，[`api.md`](api.md) §1.1）；从属对象与技术对象默认 `internal` | A（首版不进硬门禁） |

### 2.1b 运行时分层的边界（把 [`runtime.md`](runtime.md) 的四层职责变成规则）

[`runtime.md`](runtime.md) 定的是**运行时**的层职责（Controller = API 开放 / Service = 商业逻辑 / Repository = 数据读写 / 缓存 = 横切面）与两条路径（进入：认证授权 → 校验 → 默认值；返回：组装 → 聚合）。**"架构是声明的"在这里同样成立**，所以这些边界也能在设计期静态判：

| 规则 | 内容 | 等级 |
| --- | --- | --- |
| **ARCH-107** | **Controller 不得直接访问 Repository**（进入路径必须经 Service；跳层即违规，白名单须写理由） | A |
| **ARCH-108** | **缓存单点出口**：任何层取缓存只能经 `CacheProvider`；禁止自建缓存/自起 Map 缓存；**缓存键必须含租户维度** | A |
| **ARCH-109** | **拦截点只允许挂在封闭的生命周期点上**（[`runtime.md`](runtime.md) §4.2 的枚举），且 `before*` 在事务内、`after*` 在提交后且必须幂等；自定义钩子名 = 违规 | A（`after*` 幂等为 B） |
| **ARCH-110** | **装配与聚合必须是生成物**（关系/视图已声明）；手写装配、或绕过视图声明自行拼响应 = 违规（N+1 另见 ARCH-303） | A / B |

> 这四条**首版不进硬门禁**（门禁仍是 §5 的七条），先进 `mmda arch report` 的 🟡 告警清单，跑一个迭代再评估——与 ARCH-2xx 的处理方式一致。

### 2.2 耦合与内聚（有界分 + 阈值）

用 **Robert C. Martin 的包度量**（定义见 §9）：`Ca` 扇入、`Ce` 扇出、**不稳定度 `I = Ce/(Ca+Ce)`**、**抽象度 `A = Na/Nc`**、**主序列距离 `D = |A + I − 1|`**。

在 MMDA 里这两个量有确定的算法（不用猜）：

| 度量 | MMDA 里的算法 |
| --- | --- |
| `Ce` / `Ca` | 模块声明的依赖边数（出/入），来自 `biz/*.ma` 的模块引用与对象引用 |
| `I` | `Ce/(Ca+Ce)`，直接算 |
| `A`（抽象度） | `A = 该模块的对外契约数 /（对外契约数 + 具体对象数）`；**契约定为：Action 声明 + 视图声明 + 导出类型（Record/Enum 被模块外引用者）**，具体对象 = 仅模块内使用的 Record/Enum —— **✔ 定义已裁（2026-09-24）** |
| `D` | `\|A + I − 1\|` |

| 规则 | 内容 | 建议阈值（首版，可配） |
| --- | --- | --- |
| **ARCH-201** | **稳定模块必须抽象**：`Ca` 高而 `A` 低的模块 → `D` 超标，🟡 | `D ≤ 0.5` 🟢 / `0.5–0.7` 🟡 / `> 0.7` 🔴 |
| **ARCH-202** | 扇出上限：一个模块依赖的模块数过多 → 建议分层或引入中介 | `Ce > 10` 🟡 |
| **ARCH-203** | 内聚信号：① 一个 Record 的字段被多少个模块引用（**散弹式修改**信号）；② 一个模块的 Action 覆盖多少条业务流程（**上帝模块**信号） | Record 被 `> 3` 模块引用 🟡；Action 覆盖 `> 3` 条流程 🟡 |
| **ARCH-204** | 重复定义：同一概念多处定义、相似字段组未复用 → 建议提为标准字段组或 `include` | 命中即 🟡 |

### 2.3 SOLID 的操作化（逐条落到 MMDA 的语句上）

| 原则 | 在 MMDA 里的判定方式 | 等级 |
| --- | --- | --- |
| **S 单一职责** | 「被修改原因数」 ≈ 引用它的模块数 + 它承载的业务流程数 + 它被多少个角色/权限条目引用；超阈值 → 建议按能力域拆 | A（近似）+ D（最终判断） |
| **O 开闭** | 扩展必须通过 `include` / 租户扩展文件 / 新 Action / 新视图实现；**基线公共对象被租户文件直接改** = 违规（改动应表现为覆盖点声明） | A |
| **L 里氏替换** | 契约替换：实现**不得比声明更严**（前置条件加严、后置条件放宽）；可判定部分靠三端一致性用例 + AI 对照声明与实现 | B / D |
| **I 接口隔离** | 视图/角色可见字段按使用方裁剪；**敏感字段进入列表/导出/日志 = 违规**；Action 粒度过粗（一个 Action 覆盖多职责，与 S 同源） | A |
| **D 依赖倒置** | 高层模块依赖抽象：模型里**不得出现宿主实现细节**（JDBC/EF/Dapper 类型名、方言函数、目标端专有 API）——必须经 capability 声明与生成的接口 | A |

> **D 的执行细节**：跑一个目标端类型名黑名单扫描（Java/C#/TS 的类型与命名空间），命中即报。这条很便宜，却最能把"架构泄漏"挡在设计期。

### 2.4 术语与一致性

| 规则 | 内容 | 等级 |
| --- | --- | --- |
| **ARCH-401** | 术语唯一：同一概念多个名字、同名不同义 → 违规（`Terminology` 复用率看板） | A |
| **ARCH-402** | 命名与项目约定一致（命名约束注册表在校验期强制） | A |
| **ARCH-403** | 主键 / 审计 / 租户 / 状态字段在同项目内写法一致 | A |
| **ARCH-404** | 同类概念用同一种机制（枚举 vs 字典表不要混用） | A / D |

### 2.5 变更面（历史信号，项目跑起来才有）

| 规则 | 内容 | 等级 |
| --- | --- | --- |
| **ARCH-501** | **跨模块同改比例**：过去 N 次变更里有多少次同时改了 2 个以上模块 → 高说明**边界画错了**，而不是纪律不好 | C |
| **ARCH-502** | 影响面规模趋势（`diff --impact` 的对象数中位数） | C |
| **ARCH-503** | 架构熵：每次迭代的违规项数量趋势（不是绝对值，是走向） | C |

## 3. 打分模型（怎么算分而不变成玄学）

1. **硬规则**（ARCH-101~106、301/302/304、401~403）→ 只报 **pass/fail + 违规清单**，不给分。**门禁只认这些。**
2. **有界分**（ARCH-201~204、SOLID 近似项）→ 按阈值给 🟢/🟡/🔴，维度分 = 各规则加权（**权重写在 Codegen Profile 的 `quality:` 段**，随项目类型不同）。
3. **历史信号**（ARCH-501~503）→ 只进趋势看板，**永不阻塞**（否则新项目永远不合格）。
4. **总分仅用于趋势对比**（本次 vs 上次 vs 基线），报告里必须同时列出违规清单——**不允许只给总分**。

**报告形态**（`mmda arch report`）：

```
架构评估 · mes 项目 · 2026-09-24
关注点覆盖：7/8（缺口：缺「性能目标」视角承载）        ← §1 缺口清单
硬规则：🔴 2 项违规 · 🟡 3 项告警 · 其余通过
  🔴 ARCH-102 循环依赖  logistics 与 mes      证据 biz/mes.ma:31 / biz/logistics.ma:12
  🔴 ARCH-104 数据所有权冲突 DispatchPlan      由 logistics 与 mes 同时写入
模块健康：logistics D=0.62 🟡 · mes D=0.41 🟢 · base D=0.18 🟢
变更面：跨模块同改比例 34% 🟡（近 20 次变更）
建议 3 条（含影响面与级别）→ §4
```

## 4. 建议的生成（评估的另一半）

**建议模板**（缺一项都不算完整建议）：

```
规则号 → 结论 → 证据（file:line + 依赖边） → 依据（原则/标准） → 改法（具体动作）
       → 影响面（mmda diff --impact） → 变更级别（L1/L2/L3）
```

**三个真实形态的例子**：

| 场景 | 建议 |
| --- | --- |
| 循环依赖 `mes ↔ logistics` | 把两者共同需要的 `DispatchPlan` 上提为 `contracts/` 模块（单向依赖）；影响 3 个对象 / 2 个视图；**L2** |
| 上帝模块 | `logistics` 的 Action 覆盖 5 条流程、被 7 个模块引用、`D=0.62`：按能力域拆为 `logistics-dispatch` 与 `logistics-tracking`，公共部分提为契约；**L3**（含 ADR） |
| 租户直接改基线对象 | 改为 `include` 扩展文件 + 声明覆盖点，基线对象不动；**L2** |

**分工**（与 [`quality.md`](quality.md) §4 一致）：

- **规则集产生评分与违规清单**（AI 不评分——评分必须可复现、可互相核对）；
- **AI 产生建议草案与反例**：识别异味、写改法、构造"这个边界将来会怎么烂"的场景、解释历史变更；
- **架构师签字**：接受、修改或**登记例外**；
- **例外机制**：白名单文件 + 理由 + **到期复审日期**（例外本身也是可判定的：过期未复审 = 重新告警）。

## 5. 评审仪式与门禁时点

| 时点 | 跑什么 | 门禁 |
| --- | --- | --- |
| **架构基线冻结**（首次） | 全量评估 + 关注点/视角缺口清单 | 硬规则必须全绿，例外已登记 |
| **每次 L2/L3 变更** | 增量评估（本次变更触及的规则） | 新增违规必须为 0 或已登记例外 |
| **迭代 / 里程碑** | 全量 + 趋势（架构熵、跨模块同改比例） | 无硬门禁，产出改进清单 |
| **发布前** | 全量 + 与 [`quality.md`](quality.md) 的可维护性维度合并进质量报告 | A 类项达标 |
| **ATAM 式走查**（重要里程碑，半年或大改版） | 质量属性场景 → 风险点 / 敏感点 / 权衡点清单 | 人评（D），产出进 ADR |

**首版门禁范围（✔ 已裁 2026-09-24）**：硬门禁 = **ARCH-101 / 102 / 104 / 105**（分层双向、循环依赖、数据所有权、跨模块接口——全静态、最便宜、最要命）**+ ARCH-302 / 304 / 305**（开闭、接口隔离、依赖倒置的静态部分）。**ARCH-2xx 先告警不出门禁**（跑一个迭代后再评估是否转门禁），**ARCH-5xx 只进看板**。

## 6. 工具面

| 命令 | 作用 |
| --- | --- |
| `mmda arch report [--lang zh]` | 分维度 + 违规清单 + 关注点缺口 + 建议；给架构师与业务/管理层看 |
