# 测试与验收（Testing & Acceptance）

> **这份文档要解决什么**：测试不能等到编码完再补。元模型里已经声明了字段类型/长度/可空、主键与唯一、引用关系、状态迁移图、动作授权、流程网关、转↔能力——**这些声明本身就是可判定的契约**，所以用例能从架构与设计阶段**机械生成**；声明不出来的那部分（业务语义），由 AI 生成草稿、**人审用例**（而不是审代码），审过的用例冻结成**验收标准**。
> 状态：草案（2026-09-24 立；**2026-09-25 作者补充三条共识**：**UAT 的地位与时点**（§0.1）、**测试类型 = UAT 的细化与展开**（§0.2）、**用例进库与 IDE 全生命周期管理**（§8.1 / §9.1））。与 [`workflows.md`](workflows.md)（职责 / 模式 / 签字）、[`targets.md`](targets.md)（capability）、[`events.md`](lang/events.md)（幂等与重放）、[`requirements.md`](requirements.md)（`REQ-x` ↔ UAT 追溯）、[`workflows-phase.md`](workflows-phase.md)（0 站的验收准则）联动。

---

## 0. 三条原则

1. **用例是派生物**：与元模型同版本、同粒度（一对象一文件），模型改了用例**自动重算**；手写只用于声明不出来语义（少数例外，要标明原因）。
2. **每条用例必须可追溯**：`covers:` 指向声明（`data/models/{schema}/{Name}.mm#字段`）或 `req: REQ-xxx`。**无法追溯的用例标为 orphan，不计覆盖率，CI 报警**——这是防止「用例很多但什么都没验」的唯一机械办法。
3. **AI 不许当裁判**：AI 可以生成用例、可以跑、可以诊断失败原因；**判定标准只能来自声明与冻结基线**，不能来自 AI 的叙述。「AI 说没问题」永远不是验收依据。

### 0.1 UAT 的地位与时点（✔ 2026-09-25 作者共识）

> **作者原话**：「**UAT 应该在需求完成后及早出，而且是可验证的，针对 AI 可通过 hooks，而不是仅仅是文字描述，只能通过人类逐条验证，UAT 是项目交付验收的标准**」。

| 面 | 口径 | 落点 |
| --- | --- | --- |
| **地位** | **UAT = 项目交付验收的唯一标准**；其余测试（冒烟 / API / 功能 / 集成 / 性能 / 安全…）都是它的**细化与展开**（§0.2） | 本文 §5；[`quality.md`](quality.md) §5「验收交付」行 |
| **时点** | **需求完成后立即出**，随**需求基线**一起冻结——不等编码完，更不等交付前（晚出的 UAT 只能验收「已经做成了什么」，不能约束「该做成什么」） | 0 站的产物 = 需求条目 + **验收准则**（[`workflows-phase.md`](workflows-phase.md) §3）；[`requirements.md`](requirements.md) §2.2「验收面」 |
| **形态** | **必须可执行**（前置条件 + 数据 + 断言），**不是文字描述**；文字版（中文验收单）只是它的**投影**，供业务阅读与签字 | 本文 §5-②、§9 |
| **执行通道** | **AI 通过 hooks 驱动**（三端拦截点 `beforeView` / `beforeXxx` / `afterXxx`，封闭枚举见 [`runtime.md`](runtime.md) §4.2）+ `mmda test`；hooks 是**驱动与观测点**，不是判定源 | [`runtime.md`](runtime.md) §4、[`ai/tools.md`](ai/tools.md) §2.5 |
| **人的价值** | **制定验收标准 + 审核签字**——不做逐条手验 | 本文 §4 / §5；[`workflows.md`](workflows.md) §1.3 审签权限 |
| **AI 的边界** | AI 可以**跑**、可以**驱动**、可以诊断失败；**判定只能来自声明与冻结基线**（§0-3 不变） | 本文 §0-3、§4.2 六条护栏 |

**一条推论**：UAT 进需求基线后，**需求的「完成」定义 = 有可执行的 UAT**——没有可执行 UAT 的需求条目等于还没说完（`mmda check` 出 error，见 [`requirements.md`](requirements.md) §2.2）。

### 0.2 测试类型 = UAT 的细化与展开（✔ 2026-09-25 作者共识）

> **作者原话**：「**为了达成按 UAT 验收，软件开发过程中我们通常会做各种类型的测试，我认为都是围绕 UAT 的细化和展开，哪怕是产品开发，也得站在用户的角度考虑 UAT**。包括冒烟测试、API 测试、功能测试等等，我都希望在 MMDA 的世界里，能结合 AI 的能力尽可能自动化，而人类的价值发挥在辅助制定验收标准和审核」。

| 测试类型 | 它展开的是 UAT 的哪一面 | 机械判据（自动化的落点） | 跑频 | 谁定标准 / 谁审 |
| --- | --- | --- | --- | --- |
| **UAT（本体）** | 端到端业务场景：一个关键用户在一段流程里把事办成 | `suite: uat` 集合全绿 + 中文验收单签字 | 需求基线冻结时首跑、每个里程碑、交付前 | **业务人员定 + 签**；设计师协助可测化 |
| **冒烟** | UAT 的**最小可交付子集**（「这条路还走得通吗」） | `suite: smoke` 集合（从 UAT 用例里挑主干路径，建议 ≤ 20 条） | 每次生成 / 构建、部署后 | 设计师挑集；工具自动跑 |
| **功能 / API** | UAT 的**接口面**：同一场景经 API 走一遍 | 契约测试（响应 vs OAS schema，[`api.md`](api.md) §3）+ mock 造数（§4.3） | 每次提交 | 设计师 |
| **集成 / 一致性** | UAT 的**跨模块与跨端面** | 同一批用例三端结果一致（[`targets.md`](targets.md) L3） | 里程碑 + 每日 | 架构师 |
| **性能 / 并发** | UAT 的**非功能面**（「能用」之外是「够快、扛得住」） | [`quality.md`](quality.md) §2.2 默认阈值，按环境分档（§11-6） | 里程碑 | 架构师 |
| **安全** | UAT 的**权限与拒绝对抗面** | 权限矩阵用例（**含拒绝路径**，§2）+ OWASP ASVS 门禁（[`quality.md`](quality.md) §3.2） | 每次提交（子集）+ 里程碑（全量） | 架构师 |
| **变异** | **UAT 用例自身的判别力**：断言真的能抓错吗 | 存活率 ≤ 10%（§7） | 里程碑 + 每日 | 工具自动；回填由设计师确认 |

**两条纪律**：
1. **展开可以多，标准只有一个**：任何测试类型的通过**都不能替代** UAT 签字；反过来，UAT 签字**也不能豁免**机械门禁（契约、一致性、覆盖率、变异）。
2. **自动化优先，人的时间只花在两处**——**定标准**（UAT 写什么、阈值多少）与**审核**（用例签字、失败归因确认）；凡能用声明机械判定的一律交工具（§2 / §3 已列全部可机械生成的用例）。

## 1. 用例的四个来源与审签

| 来源 | 典型内容 | 生成者 | 审签（按 §1.3 权限） | 是否计入验收 |
| --- | --- | --- | --- | --- |
| **`mechanical` 机械生成** | 长度/精度/可空边界、唯一冲突、引用完整性、状态迁移矩阵、权限矩阵 | `mmda test-gen` | 设计师（语义对不对） | **是**（审签即生效；单人模式 self-approve） |
| **`snapshot` 契约快照** | IR / 接口签名 / DDL / 渲染描述的快照比对 | 工具 | 架构师（确认这次变更是有意的） | **是** |
| **`ai` AI 生成** | 业务场景、组合状态、异常路径、跨字段联动 | AI Agent | **业务人员（业务对不对）+ 设计师（能不能测）** | **仅当 `reviewedBy` 非空**才计入；否则留库标 `draft` |
| **`manual` 手写** | 探索性、性能、安全、并发 | 程序员 | 程序员 / 架构师 | 是 |

> 关键设计：**机械用例不需要"发明"，只需要"确认"**——所以它的审签成本极低（看清单即可），而 AI 用例的审签成本高，必须双签。

## 2. 架构阶段就能生成的用例

架构师的声明都是可判定的，所以这一层不需要等代码：

| 声明（来源） | 生成什么用例 | 断言什么 |
| --- | --- | --- |
| `flow/roles/*.mr`（角色 / 权限 / scope） | **权限矩阵**：role × action × scope 全覆盖 | 允许的角色能执行；未授权角色被拒（**拒绝路径必须有用例**） |
| 数据范围（OWNER / WORKGROUP / DEPARTMENT / ALL） | 范围样本用例 | OWNER 只看到自己创建的；跨部门不可见 |
| `biz/*.ma` 模块依赖 | 边界用例 | 跨模块只能用声明接口；反向依赖 = 校验/编译失败 |
| `flow/*.mb`（BPMN 池/活动/网关） | 路径覆盖 | 每个网关分支有样本；每个节点有触发者与结果事件；无孤立节点 |
| `flow/*.mf`（数据流：节点图 / DFD / 数据映射图） | 路径覆盖 | 每个端点有上下游；映射字段类型兼容；无孤立节点 |
| `flow/converters/*.mc` | 映射用例 | 字段类型兼容；抽样值双向等价；必填字段不可丢 |
| capability 声明 | 能力门禁用例 | 语言用到的能力在目标端必须声明（缺失 → 生成期报错）；同一声明三端行为一致 |
| 多租户扩展文件（include，B4） | 隔离与叠加用例 | 租户扩展不破坏基线；基线升级后扩展仍能加载 |

**价值**：架构评审从"看着办"变成"跑一遍权限矩阵与路径覆盖"，而且这些用例在写第一行代码之前就存在——**它们定义了什么叫"做完"**。

## 3. 设计阶段就能生成的用例

| 声明 | 生成什么用例 | 边界取法 |
| --- | --- | --- |
| 字段类型 / 长度 / 精度 / 可空 / 默认值 | 等价类 + 边界值 | **min-1 / min / max / max+1**、空值、超长、类型不符 |
| `@Id` / 唯一约束 / `@Partitioned` | 唯一冲突、分区键必填 | 重复值、缺失分区键 |
| `@Ref` / `@One` / `@Many` | 引用完整性 | 引用不存在、删除被引用（级联或拒绝）、自引用 |
| `constraint` / `formula` | 约束表达式边界 | 纯函数 ⇒ 输入域可抽样穷举；非法表达式不许进真源 |
| `@Computed` | 确定性用例 | 同输入必同输出、可重放（与 [`events.md`](lang/events.md) 的重放要求一致） |
| `@State` + STM（`data/stms/*.ms`） | **迁移矩阵**：每对合法迁移 1 正例，每类非法迁移 1 反例；可达性 | 从初始态到每个状态都存在路径；每个 action 有前置状态与授权 |
| `ui/**/*.mi` + i18n 词条 | 呈现用例 | 可见/必填/只读与元数据一致；无空标签；五视图可渲染（[`presentation.md`](lang/presentation.md) §5.1 渲染描述） |

**设计阶段的"完成"定义**：`validate` 零 error **且** 机械用例全绿。设计师交付的不是"模型文件"，是"模型文件 + 那批自动长出来的用例"。

## 4. AI 生成用例 + 人工审核（防幻觉的具体做法）

**AI 的输入**：相关元模型子集 + 需求原文 + 既有用例（few-shot 对齐风格）+ `conventions.md`。
**AI 的输出**（三样缺一不算交付）：
1. **用例草稿**（带 `covers:` / `req:` 追溯）；
2. **审阅清单**：我为什么加这条、覆盖了哪个风险、**哪一条我拿不准**；
3. **未覆盖声明清单**：哪些声明我没能写出用例（这比用例本身更有价值——它暴露理解的空洞）。

**人工审核 = 签字**，按 [`workflows.md`](workflows.md) §1.3 的权限落到人：业务语义归业务人员、可测性归设计师；模式（单人/结对/团队）决定签字人数（§1.1）。

**三条禁令**：
- 不许 AI 自评通过（AI 只能给出「可能通过」的预测，判定由工具与基线给出）；
- 不许拿"AI 说没问题"当验收依据；
- 不许 AI 直接修改**已冻结基线**的用例——只能提变更（走变更分级）。

**IDE 落点**：设计器里选中一个对象 → 「生成用例」→ 草稿进**审阅面板**（逐条可勾选/改期望值/标注"不接受，理由…"）→ 签字 → 冻结。审阅面板里 AI 的"拿不准"清单排在最上面。

### 4.1 AI 增强能力总表

| # | 能力 | 输入 | 产出 | 决定权 | 成本 |
| --- | --- | --- | --- | --- | --- |
| 1 | **用例生成**（需求 → 草稿） | 需求原文 / 会议纪要 + 元模型子集 + 既有用例 | 用例草稿（带 `covers`/`req`）+ **未覆盖声明清单** | 业务 + 设计师双签 | 中 |
| 2 | **测试数据工厂** | 类型 / 约束 / 引用图 | 合法数据集（引用完整性满足）+ 每个约束**一对一违反**的非法集 | 设计师抽查 | 低（机械为主） |
| 3 | **用例自愈**（期望值维护） | `--impact` 的「需改期望值」清单 | 候选修正补丁——**出补丁，不静默改** | 设计师确认 | 低 |
| 4 | **失败诊断 triage** | 失败明细 + 本次 diff + 相关声明 | 分类报告：模型漏改 / 实现漏改 / 期望值过时 + 建议 | AI 出报告，改动归人 | 低 |
| 5 | **用例优先级**（跑哪些） | 影响面 + 变更级别 + 历史失败率 | 排序子集：提交跑高价值、每日跑全量 | 工具自动 | 低 |
| 6 | **属性 / 模糊测试** | `constraint` / `formula` 的纯函数表达式、网关分支 | 属性用例 + 对抗样本 | 设计师确认 | 中 |
| 7 | **变异回填**（缺口 → 用例） | 存活的变异 | 能杀死该变异的用例草稿 | 设计师确认 | 中 |
| 8 | **用例质量评分** | 用例 + 声明 + 变异结果 + 历史执行 | 质量分 + 分层（黄金 / 普通 / 草稿）+ 理由 | **分只用于排序；晋升由人** | 中 |
| 9 | **覆盖率看板** | 声明 × 用例对账 | §6 各维度 + 变更覆盖 + 缺陷回溯覆盖 | 门禁自动 | 低 |
| 10 | **中文验收单生成** | 黄金用例集 | 验收单（供业务签字） | 业务签字 | 低 |

**落地顺序建议**：先上**纯机械的四项**（孤儿检测、变更覆盖、弱断言检测、变异测试）——它们最便宜、最能防"用例装饰"；AI 那几项（1/2/4/6）随后，因为它们需要前四者当裁判。

> **第 2 项（测试数据工厂）已由作者 2026-09-24 裁决扩展为两层造数**（机械层 + AI 语义层），见 §4.3——这是"AI 提速写用例"的主入口。

### 4.2 AI 增强的六条护栏

1. **AI 只能提议**：不能晋升用例、不能签字、不能修改已冻结基线。
2. **所有 AI 产出必须带出处**：声明点 / 需求号 / 失败记录 + 置信度。凭空来的断言不算用例。
3. **冲突以声明为准**：AI 的断言与元模型声明矛盾时，声明赢，并把它记为「AI 理解偏差」——这是改进规则与提示词的输入。
4. **每个 AI 能力自己要有回归**：例如变异回填产出的用例必须真能杀死该变异，否则丢弃（否则"AI 补测试"会变成刷覆盖率）。
5. **质量分与覆盖率不是验收依据**，只用于排序与提示。验收依据永远只有三样：跑基线全绿 + 快照差异已确认 + 验收单已签字。
6. **用数字评估这套增强本身**：统计 AI 参与度（生成/修改/诊断占比）、回归逃逸率、每千行模型变更引入的缺陷数。**不凭感觉说"AI 提升了质量"**。

### 4.3 Mock 数据生成：机械打底 + **AI 填语义**（作者裁决 2026-09-24）

> 原话：「API 测试要能借助 AI 的能力自动生成 mock 数据，这个也很关键，这是撰写测试用例的提速手段。」

**为什么这条重要**：用例的**结构**早已由声明定了（§2 / §3 的机械生成、[`api.md`](api.md) §3.3 的端点与 schema），真正的瓶颈是**数据**——写一条边界用例，卡人的往往是"造一条像样的数据"：要满足外键、要满足跨字段联动、还要在业务上说得通。

**两层分工（不可混）**：

| 层 | 谁做 | 造什么 | 性质 |
| --- | --- | --- | --- |
| **① 机械层** | Rust 内核，**零 AI** | **引用图拓扑排序**后逐表造数（先父后子，满足外键）；枚举取值；长度 / 精度 / 范围的 min-1 / min / max / max+1；空值与超长；日期与时区边界；STM **可达状态** | **可信地基**：可复现（固定种子）、可进基线、契约测试直接用它 |
| **② AI 层** | AI Agent | 中文业务数据（公司名 / 物料 / 部门岗位）、**跨字段联动**（"已审批的工单必有审批人与时间"）、业务合理的数值分布、**刁钻样本**（越界、null、超长、时区跨日、`decimal` 精度末位、并发重复键） | **提速手段**：让人（业务 / 设计师）**读得懂、审得动**；也是杀死变异体（§7）的输入来源 |

**四条护栏**（与 §4.2 同源，这里是数据专条）：

1. **AI 不得发明结构**：字段名、枚举值、状态名**只能取自声明**——出现声明里没有的值**直接丢弃**（不是提醒，是判废）；
2. **每条数据过两道校验**：JSON Schema（由 [`api.md`](api.md) §3.5 生成）+ 元数据约束（`constraint` / `formula` / 唯一键 / 引用完整性）；**不过校验的数据不许进基线**（否则 mock 数据会污染契约测试）；
3. **可复现**：固定随机种子 + 记录 **provenance**（模型、提示词版本、种子、时间）——✔ **已裁（2026-09-24）：二者随数据一起进版本控制**（固化，能重建同一次造数）；
4. **AI 造的是输入层，不是断言层**：数据上 AI 可以放开（**这正是不需要双签的原因**），**断言与基线仍只来自声明 + 人签字**（§4.2-1）。

**与"用例是派生物"的衔接**：数据是派生物、断言是派生物 ⇒ 端点 `example`（[`api.md`](api.md) §3.5）与 mock server（[`api.md`](api.md) §4）**共用同一份造数结果**。分界线一句话：**AI 造数不用双签，AI 断言必须双签。**

**命令面**：`mmda mock --from meta [--ai] --seed <n>`、`mmda mock serve`（起 mock server）；产出落 `generated/<target>/mock/`（generated 区，不手改）。

**用途三面**：① 提速写用例（先有数据再写期望值）；② mock server 供前端 `vui` / `rui` 与第三方并行开发；③ 演示与培训（不碰真库）。

## 5. 用例作为验收标准（三层验收物）

| 验收物 | 形态 | 谁签字 | 用途 |
| --- | --- | --- | --- |
| ① **可执行用例** | `mmda test --target java,csharp,ts` 全绿 | 设计师（机械）/ 业务人员 + 设计师（AI） | 技术验收的机器判定 |
| ② **中文验收单** | 由用例**反生成**：支持哪些操作、什么条件下被拒、边界是什么、谁有权做什么 | **业务人员** | 业务验收；他不看代码，只看这张单子 |
| ③ **契约快照差异** | IR / 接口签名 / DDL / 渲染描述的差异清单 | 架构师 | 确认"这次变更是有意的" |
| ④ **质量报告** | ISO/IEC 25010 九维 × 子特性：证据 / 等级 / 达标或未达标或未评估；**含架构评估**（分层/循环/所有权/SOLID 操作化，见 [`architecture-review.md`](architecture-review.md)） | 架构师（A/B 项）/ 业务与管理层（阅读） | 覆盖"用例之外"的质量面，见 [`quality.md`](quality.md) §3 |

**基线（baseline）机制**：验收前把用例集冻结为 `baseline/<版本>`，此后所有改动都对照它算差异。**交付 = 跑基线全绿 + 快照差异已确认 + 验收单已签字**，三者缺一不算交付。

**变更后的重算**：`mmda diff --impact` 输出「**受影响的用例清单**」——哪些用例因这次变更而新增、失效、或期望值要改（例：字段长度 30→40 ⇒ 有一个边界用例的期望值必须变）。模型改了却没人看这份清单，就等于悄悄改了验收标准。

## 6. 覆盖率的算法（按声明维度，不用"行覆盖率"糊弄）

| 维度 | 定义 | 建议门禁 |
| --- | --- | --- |
| 字段覆盖 | 每个字段 ≥ 1 组边界值 + 1 组非法值 | 100% |
| 迁移覆盖 | 每对合法迁移有正例；每类非法迁移有反例；状态可达性 100% | 100% |
| 权限覆盖 | role × action × scope 全覆盖（**含拒绝路径**） | 100% |
| 能力覆盖 | 每个 capability 至少一条跨端一致用例 | 100% |
| 需求覆盖 | 每条 `REQ-x` 至少 1 条用例 | ≥ 90% |
| 有效性 | 变异存活率（§7） | ≤ 阈值（待定，§11） |

覆盖率全部**由声明算出**，所以是"能指着说缺哪条"，而不是一个百分比数字。

### 6.1 AI 增强的三个覆盖维度

| 维度 | 定义 | 为什么重要 |
| --- | --- | --- |
| **变更覆盖** | 本次 diff 的每个语义变更点，是否都有用例 `covers` 命中 | **最有用的一项**：改了 5 个字段只有 3 个被用例碰到 = 60%，一眼看出漏了哪里 |
| **缺陷回溯覆盖** | 历史缺陷（bug 号）是否都留下了回归用例（defect → test 追溯） | 防同一个坑踩两次；也让"修了但没留下用例"变成可见的债 |
| **分支覆盖** | `constraint` / `formula`、流程网关的分支是否都被样本走到 | 表达式是纯函数 ⇒ 分支可枚举、可穷尽，没有借口漏 |

**造假反制**（覆盖率是最容易被刷的指标）：① `covers` 必须指向**具体声明点**，不是指向文件；② 机械做「声明 × 用例」的笛卡尔对账，而不是信任用例自己填的标签；③ **变异存活率是最终裁判**——覆盖率 100% 但变异存活率高，说明用例是装饰。

### 6.2 用例质量评估（可算、可门禁、可排序）

| # | 维度 | 判据 | 弱用例的典型表现 |
| --- | --- | --- | --- |
| 1 | 可追溯 | 有 `covers`/`req` 且指向存在的声明 | 孤儿用例（0 分） |
| 2 | **断言强度** | 断言具体结果（值 / 错误码 / 状态），而非"不报错" | 只 `expect { ok }` |
| 3 | 独立可重放 | 不依赖执行顺序、真实时间、随机 | 依赖 `now()`、依赖上一条用例的副作用 |
| 4 | 边界与否定路径 | 含边界值与拒绝路径 | 只测 happy path |
| 5 | **判别力** | 能否杀死对应变异（最硬指标） | 变异存活 |
| 6 | 稳定性 | 历史通过/失败抖动（flaky 率） | 时红时绿 |
| 7 | 业务可审 | 能生成人话验收单并被业务人员看懂 | 术语堆砌、看不出业务含义 |

**分层用法**（不是所有用例同等重要）：

| 层 | 含义 | 门禁 |
| --- | --- | --- |
| **黄金** | 进基线、必须全绿、验收单由它生成 | 交付硬门禁 |
| **普通** | 有效但非交付阻塞 | 跑、报告，不阻塞 |
| **草稿** | AI 生成未签字 / 新生成待审 | 不计入验收 |

新生成的 AI 用例默认落**草稿**，经质量分排序后由人审阅签字晋升。**AI 可以给分与理由，晋升与签字必须是人。**

## 7. 变异测试（验证用例真的能抓错）

**机械变异**（由工具自动施加，一次一个）：长度 30→31、必填改可空、删一条状态迁移、放宽一个权限、改一处 Converter 映射、去掉一个 capability 声明、把 `@Computed` 改成依赖时间。

**期望**：对应的用例必须变红。**存活的变异 = 用例缺口** → 自动回填用例草稿（AI 生成 + 人审）。

**跑频**：里程碑 + 每日定时（不进每次提交，太慢）。它是「AI 时代最需要的自动补测试手段」——因为用例大都可以自动生成时，唯一稀缺的是**知道哪些用例还没生成**。

## 9. 用例文件形态

**后缀已裁（2026-09-25 改判）**：**测试用例就是 `.m`**（语言文件统一后缀），住**阶段根 `tests/`**，与模型同粒度、**一对象一文件**（[`project.md`](lang/project.md) §1.2 / §11；原 `.mt` 分片后缀已作废）。**语法形态待裁**（§11 待裁第 9 条，随语法专题）。

一对象一文件，与模型同粒度：

```
# tests/order/Order.m（语言文件后缀统一为 .m）
test "长度上限 30" covers data/models/order/Order.mm#code
  source: mechanical
  given  { code: "A"*31 }
  expect { reject(reason: "长度超出 30") }

test "审批必须从草稿发起" covers data/stms/order/OrderStatus.ms
  source: ai
  reviewedBy: { business: 张三, designer: 李四 }
  given  { order.status: APPROVED }
  when   { action submit(order) }
  expect { reject(reason: "前置状态不满足") }
```

必需字段：`covers` / 来源 `source` / `reviewedBy`（AI 用例必须非空）/ `baseline`。

### 9.1 用例进库与三个管理维度（分类 / 集合 / 状态）

> **✔ 2026-09-25 作者口径**：原话「**我希望测试用例也进 m 语言，跟需求一样，我会将测试用例（testing case）存入数据库，进行分类、分集合、分状态跟踪管理。这样我的 IDE 就变为一个 SDLC 完整生命周期管理工具**」。

**与需求同构**（[`requirements.md`](requirements.md) §2.2 同一套逻辑）：**文件（`.m`，在 `tests/`，git）是唯一真源 → 进库像元对象一样落表 → IDE 直读管理面**；运行期在库里改了用例，**必须回写文件**。

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| **来源 `source`**（已有，§1） | `mechanical` / `snapshot` / `ai` / `manual` | 「谁生成的」——决定审签强度 |
| **类型 `kind`**（新） | `uat` / `smoke` / `api` / `functional` / `integration` / `perf` / `security` / `conformance` | 「展开 UAT 的哪一面」（§0.2）；**与 `source` 正交**——一条 UAT 用例可以是 `mechanical`，也可以是 `ai` |
| **集合 `suite`**（新） | `uat-core` / `smoke` / `regression` / `daily` / `milestone` / `perf` / `security`… | 「什么时候跑它」——一条用例可属多个集合；与「用例优先级」（§4.1-5）是同一件事的两面 |
| **生命周期状态**（新） | `draft` → `reviewed` → `frozen`（进 `baseline/<版本>`）→ `deprecated` | 只有 `frozen` 的用例算验收依据（§5；§6.2 分层的「黄金」） |
| **执行状态**（新） | `not-run` / `pass` / `fail` / `blocked` / `stale` | `stale` = 声明或需求已变、期望值未重算（`--impact` 的输出，§5） |

**可机检的三条**：
1. `kind: uat` 的用例**必须**有 `req: REQ-xxx` 且 `reviewedBy` 非空——否则 `mmda check` 出 **error**（UAT 没有需求锚点 = 无法验收）；
2. `smoke` 集合**必须是 `uat` 集合的子集**（主干路径不能自成一派）——出 warning；
3. 集合**不许有孤儿**：空集合、或指向已废弃用例的集合——出 warning（防「集合还在跑，内容早已死」）。

**库表形态待裁**（§11-15）：拟 `meta_test` + `meta_test_suite`（用例 ↔ 集合多对多）+ `meta_test_run`（执行历史：时间 / 目标端 / 结果 / 耗时 / 失败原因）。
