# 差异对照：需求定义（标准侧 vs `mmda_alm` 库侧）

> **用途**：把「现行规范里的需求定义」与「`mmda_alm` 库里的需求定义」逐条摊开，交作者勾选哪些进标准。
> **✔ 2026-09-28 作者裁定（两轮，先落地）**：关键字 **`intent`**（不用 `requirement`）、编号 **`INT-<NNN>` 纯序号**（D6 去掉模块段）、`layer` **只两档**（D1 只保留业务 / 用户）、**`subject` 必填**（原 `area`）、**BUSINESS 不得直挂 usecase**、**UAT 挂 intent**（D7 方向定）、**usecase 进语言并上 UML 图形**（D8 进标准 ✔）；**三轮**：**D0 = A 元对象**（意图落 `Meta*`，`mmda_alm.requirement` 降为投影（**⤴ 四轮：该库仅参考、将废除，不再投影**））、**粒度 = 一文件可放多条 `intent`**（与 `record` 同，可 `import` / 相互引用）、**暂时不要多行字面量**、**建模侧回指 `satisfies UC-…` / `satisfies INT-…` 都允许**。规范见 [`../../lang/intent.md`](../../lang/intent.md)；**落库表结构**见 [`../../lang/intent-store.md`](../../lang/intent-store.md)（`MetaIntent` 元对象表族）；下表未打勾的条目**仍待裁**。
> **取数**：标准侧 = `doc/requirements.md` §2 / §2.1 / §2.2 / §3 / §7 + `doc/lang/project.md` §1 + `doc/testing.md` §0.1 / §1 / §9.1 + `doc/lang/meta-model.md` §8.1 + `doc/naming.md` §1 / §3.3；库侧 = `mmda_alm.requirement` / `requirementdependency` / `requirementmodule` / `testcase` / `bug` / `tag` / `changelog` 的实测 DDL（本机 `127.0.0.1:3306`）。
> **⤴ 2026-09-29 四轮（作者裁）**：**`mmda_alm` 仅作参考，不再作为投影目标，将来废除**（作者原话：「**mmda_alm仅仅给你作参考，不用投影，以后废除了**」）——本表的定位从**「库侧该不该补」改成「旧库留给我们的设计输入」**：**「只库有 → 要不要收进标准」与「两边冲突」仍作设计输入**；**「只标准有 → 库里要不要补」与「库自身不一致 → 要修」全部失效**。落库真源只剩内核 `MetaIntent` 族（[`../../lang/intent-store.md`](../../lang/intent-store.md) §0）。
> **一句话结论**：**标准侧目前是骨架（只有语法位与门禁，没有字段定义），库侧是完整字段集（29 列 + 3 张关联表）**——所以差异的主体是「库有、标准无」，真正**两边都写了且互相冲突**的有 6 条（**D0** / D3 / D5 / D7 / D9 / D11）——其中 **D0 是总闸**，它决定其余各条往哪边收敛。

## ① 只库有：要不要进标准？

### D1 · 需求层次（业务 / 用户 / 功能）
| | |
| --- | --- |
| 标准（✔ 2026-09-28 更新） | **两层意图是主轴**：`layer` 只两档 `BUSINESS` / `USER`；**层号 = 归属节点层级**（BUSINESS→System/Module、USER→Module/Feature），由 S2 侧 `satisfies` 回指算出，`mmda check` error（[`../../lang/intent.md`](../../lang/intent.md) §2.1 / §7-12）。**功能层不进意图**（归 S2 建模声明点） |
| 库 | **无对应字段**。`requirementType` 是 Kano 模型，不是层次 |
| 建议 | **进标准**（`@Layer` 保留）。库里两个出路：**A** 补 `layer` 列；**B** 不补，由 `moduleCode` 的模块层级推导（推荐 B，避免两处真源） |

### D2 · 需求类型（Kano 价值分类）
| | |
| --- | --- |
| 标准 | 无 |
| 库 | `requirementType` tinyint：`BASIC/DESIRED/ATTRACTIVE/INDIFFERENT/UNDESIRED`（0/1/2/4/5） |
| 建议 | **进标准**（`@Type`）—— 它与 D1 的层次**正交**（一个是「谁的需求」，一个是「对谁的价值」），互不替代 |

### D4 · 优先级
| | |
| --- | --- |
| 标准 | 只有一个名字 `@Priority`，**取值未定义**（`project.md` §1） |
| 库 | **两个字段**：`importance`（UNKNOWN/IMPORTANT/VERY_IMPORTANT）+ `urgency`（NORMAL/SENIOR/URGENT） |
| 建议 | **标准采双字段**（`@Importance` + `@Priority`=urgency），`@Priority` 收窄为紧急性的名字；单字段表达不了「重要且不急」 |

### D10 · 需求间依赖
| | |
| --- | --- |
| 标准 | 无 |
| 库 | `requirementdependency`：自引用 M:N（`requirementID` → `preRequirementID`）+ 双向 FK 级联 |
| 建议 | **进标准**（`@DependsOn` / `@Many`）。排程与「前置需求未完成」守卫都需要它 |

### D12 · 标签
| | |
| --- | --- |
| 标准 | 无通用机制（`tags` 只在个别 record 里出现） |
| 库 | `requirement.tags` 逗号串 + 独立 `tag` 表（`tagName` / `tagFor` / `usedCount` / `lastUsed`，注释写「支持所有实体对象打标签」） |
| 建议 | 若要把标签做成**跨对象通用能力**就进标准（`@Tag` + 统一 `tag` 表 + 实例逗号串）；否则留作应用自定义。**注意**：逗号串与 `tag` 表已经是两份真源 |

### D13 · 责任人 / 部门 / 审计
| | |
| --- | --- |
| 标准 | 只有 Role（设计元素，谁持有 Role 是 IDE 配置，`meta-model.md` §8.1）；审计字段无通用规定 |
| 库 | `deptID` / `creatorID` / `createDate` / `lastModifierID` / `lastModified` / `ownerID` / `ownerDeptID`（7 件套，`bom` / `bug` / `testcase` 表**完全相同**） |
| 建议 | 这 7 件套事实上是**跨表通用**，建议进标准做成可复用的接口 / 基类型（如 `IAuditable` / `IOwnable`），而不是每表抄一遍。**另**：标准有 Role 概念但库里需求无 `roleCode`（触发者）落点 —— 要不要补？ |

### D14 · 排程 / 计划
| | |
| --- | --- |
| 标准 | 无 |
| 库 | `manDays` / `expectedStart` / `expectedFinish` / `expectedPeriod` / `taskColor` / `constraintType` / `constraintDate` / `actualStart` / `actualFinish` / `actualPeriod`（甘特 / 项目管理一整套） |
| 建议 | 它更像**计划 / 任务**属性（`mmda_pm` 域）。建议抽 `PlanItem` 基类型供需求继承；**不建议**把 10 个排程字段写进需求的标准定义 |

### D16 · 需求来源
| | |
| --- | --- |
| 标准 | §7-6 建议「业务人员口述 → AI 转候选条目 + 候选模型差异 → 设计师落盘」 |
| 库 | 无 `source` / `origin` 字段 |
| 建议 | 可选补 `source`（人 / AI / 客户 / 法规），否则算不出「AI 采纳存活率」这类指标 |

## ② 只标准有：库里要不要补？

### D6 · 编号
| | |
| --- | --- |
| 标准（✔ 2026-09-28 更新） | **`INT-<NNN>`**（意图）/ **`UC-<NNN>`**（用例）——**纯序号、不含模块段**（`REQ-<模块编码>-<NNN>` 作废）；**内核签发、人不手写、签发即固定**；`@Unique`（[`../../lang/intent.md`](../../lang/intent.md) §5） |
| 库 | `requirementNo varchar(36)`，**没有任何索引**（连普通索引都没有） |
| 建议 | 标准侧保留；库侧补 **unique**，并让内核/服务层保证格式。**无唯一约束 = 编号可重复，追溯链会静默断** |

### D8 · 用例（用户需求）与需求的关系
| | |
| --- | --- |
| 标准（✔ 2026-09-28 已裁） | **`usecase` 进语言**（一等 partType，`usecase UC-… : INT-…`，住 `intents/`）、**UML 用例图 / 活动图**图形投影（适配器 `muc-uml`）；用户需求 = `intent`（USER 层）+ `usecase` 细化 |
| 库 | **无 usecase 表**；只有 `testcase`（测试用例，属 S3 验收物） |
| 建议 | 先定标准侧 `usecase` 形态；库里要不要建 `usecase` 表随之定 |

### D15 · 修订 / 变更日志
| | |
| --- | --- |
| 标准 | `revision` + ChangeLog + 变更分级 L0–L3 + `mmda diff --impact`（`workflows.md` §8） |
| 库 | `requirement.revision` **有**；但**没有 `changeLogId`**（同库的 `bom` 表有 `changeLogId`） |
| 建议 | 进标准；库补 `changeLogId`，否则需求的变更不可 undo / 不可审计 |

## ③ 两边冲突：必须二选一

### D0 · 意图的本质：元对象（路线 A）还是应用业务表（路线 B）—— **总闸** ✔ **已裁（2026-09-28）：A 元对象**

| | |
| --- | --- |
| 标准 | `requirements.md` §2.2 原话：「**像元对象一样落 `Meta*` 表**」（拟 `Meta*` 元对象族 + 关联表）；且意图是**与 `record` / `enum` / `stm` / `role` 同级的一等声明**、是**元语言要素**（`project.md` §1 首关键字清单）——**语法由语言给定，不是用户自定义的 record** |
| 库 | 一张**普通业务表** `mmda_alm.requirement`（29 列，混入排程 `manDays`/`expected*`/`actual*` 与审计 7 件套），**无 `Meta` 前缀、不在元数据库** |
| 冲突 | 「元对象」⇒ 宿主应是内核元模型（`Meta*` 族，跨项目通用，`mmda check` 的意图门禁与追溯有共同落点）；「业务表」⇒ 意图只是 ALM 一个应用的业务数据，门禁没有共同宿主、跨项目追溯不可查 |
| ✔ 裁定 | **A 元对象**（2026-09-28 作者）：落内核 `Meta*` 族（拟 `MetaIntent` + 关联表）；~~`mmda_alm.requirement` **降为投影 / 缓存**（不再真源）~~ —— **⤴ 2026-09-29 四轮：该库仅参考、将废除，投影层取消**。连带：D3（归属）/ D5（状态）/ D7（UAT 追溯）都应收进元模型侧；D14（排程字段 `manDays`/`expected*`/`actual*`）**不进**意图元对象——那是 ALM 应用自己的业务数据 |
| 表结构 | 已起草 **[`../../lang/intent-store.md`](../../lang/intent-store.md)**（`MetaIntent` 元对象表族：列 ↔ 语言子句逐条对、正文双列、关联表形态、~~与 `requirement` 的投影映射~~（**⤴ 四轮废除**）；**命名 `Meta*`（`MetaIntent`）/ 审计与状态不进 —— ✔ 2026-09-28；正文取双列（`why` / `what` 落主表，不建子表）—— ✔ 2026-09-29 改裁**） |
| 仍开放 | 意图进库的**写入口**（IDE 的 CRUD 是「改文件 + 回写库」还是允许直改库）→ [`../../requirements.md`](../../requirements.md) §7-11 |
### D3 · 归属（模块）
| | |
| --- | --- |
| 标准 | **单一** `@Feature M.01.001`（按 moduleCode 找模块节点，S1→S2 的锚，`project.md` §1.3）；每条需求必须有归属 |
| 库 | **双轨**：`requirement.moduleCode`（可空，单归属）**＋** `requirementmodule` 关联表（多归属，且**无外键**） |
| 冲突 | 一条需求到底挂一个模块还是多个？两处同时写 = 两份真源 |
| 选项 | **A** 只留单归属（删 `requirementmodule`）／ **B** 只留多归属（删 `moduleCode` 列）／ **C** 单归属为主 + 多归属为辅（标准需明确谁优先） |

### D5 · 状态
| | |
| --- | --- |
| 标准 | `@Status` + **`stm` 状态机**承载流转（枚举做值域、状态机做怎么走，`guide/enums.md` §5）；取值未定义 |
| 库 | `status` 四值：`NEW` / `ACCEPTED` / `IMPLEMENTED` / `REJECTED`——**没有草拟 / 评审中 / 已变更**；且**可空**（无 NOT NULL）；库中无状态机 |
| 冲突 | 标准要求流转走 `stm`，库侧无状态机；且库的取值域与标准未对齐 |
| 选项 | **A** 取值以库为准并补 `stm` ／ **B** 库补草拟 / 评审态 ／ **C** 每项目自定义，只进 Profile 不进标准 |

### D7 · 验收准则 / UAT（**最大的缺口**）
| | |
| --- | --- |
| 标准（✔ 2026-09-28 更新） | **每条 USER 意图必须带可执行 UAT**（`req: INT-…`，可选 `covers: UC-…`），缺失 = `mmda check` **error**；UAT 随**意图基线**冻结；不可追溯的用例算 orphan；追溯链 `INT-… → usecase → 声明点 → 生成物 → 指标 → 缺陷 → 回归`（[`../../lang/intent.md`](../../lang/intent.md) §4 / §6、`requirements.md` §2.2、`testing.md` §1 / §9.1、`quality.md` §5） |
| 库 | `requirement` **无验收字段**；`testcase` **无 `requirementID`**（只有 `moduleCode`）；`bug` 有 `testCaseID` 但**无 `requirementID`** |
| 冲突 | **标准的核心门禁在库里完全没有落点** —— 需求→用例→缺陷→回归这条链在库侧是断的 |
| 选项 | **A** `testcase` 补 `requirementID`（直接外键）／ **B** 新建 `requirementtestcase` 关联表（M:N，一个用例可覆盖多条需求）／ **C** 只在文件侧保证，库侧不建（则 IDE 的追溯矩阵无数据源） |

### D9 · 标题与描述
| | |
| --- | --- |
| 标准 | `/// <label> : <description>`；且 **`description` 不进业务载荷**（只进设计真源 / `mmda doc` / IDE / comments 层，`meta-model.md` §6.2 / §6.3） |
| 库 | `requirementTitle varchar(255) NOT NULL` + `requirementDesc text NOT NULL` —— **是必需的业务数据** |
| 冲突 | 标准说描述不进载荷，库说描述是必需列 |
| 选项 | **A** 需求条目例外：正文即业务数据（`@Title` / `@Desc` 或字段体），`///` 只留 label（**推荐**——需求描述本来就是给人和 AI 读的载荷）／ **B** 描述走 comments 层、库里去掉 `requirementDesc`（则需求在库里没有正文，IDE 表格看不到内容） |

### D11 · 层级结构（需求树 vs 模块树）
| | |
| --- | --- |
| 标准 | 层级靠**模块树**（System / Module / Feature）+ `@Layer` 推导（`requirements.md` §2.1） |
| 库 | `parentRequirementID` —— 一套**独立的需求树**（自引用） |
| 冲突 | 两套树并存 ⇒ 归属双重表达，容易互相打架 |
| 选项 | **A** 只留模块树（删 `parentRequirementID`）／ **B** 只留需求树（`@Layer` 改由需求树深度决定）／ **C** 两套都留但明确定义分工（如需求树只表达「拆解」，归属仍以 moduleCode 为准） |

## ④ 库自身的不一致（与标准无关，但要修）

| # | 问题 | 证据 |
| --- | --- | --- |
| L1 | `manDays` 类型打架 | C# `public int? manDays` ↔ DDL `decimal(18,1)` |
| L2 | `requirementNo` 长度打架 | C# `[MaxLength(15)]` ↔ DDL `varchar(36)` |
| L3 | `requirementNo` **无唯一索引** | DDL 的 KEY 列表里没有它（同 D6） |
| L4 | `tags` / `taskColor` 字符集与表不一致 | 两列显式 `CHARACTER SET utf8 COLLATE utf8_general_ci`，表默认 `utf8mb4_bin` |
| L5 | `status` 可空 | `smallint(6) DEFAULT 0`，无 `NOT NULL` |
| L6 | 表名 / 列名大小写与命名规范冲突 | 表 `requirement`（小写）vs `naming.md` 要 PascalCase；列 `requirementID`/`deptID`（大写 `ID`）vs camelCase、语料写 `bomId` |
| L7 | 枚举与字典表口径不统一 | 多数类型做成 tinyint + 注释，`testtype` 却做成独立表（`architecture-review.md` ARCH-204 要求不混用） |
| L8 | 枚举值域在列注释里重复一份 | 注释 `0;BASIC;基本需求\|1;DESIRED;…`；标准说枚举本身即真源、不必重复 |
| L9 | `requirementmodule` **无外键** | 只有复合主键，`requirement` 删除后关联行残留 |
| L10 | 需求 → 缺陷追溯断 | `bug` 有 `testCaseID` / `testStepID`，无 `requirementID`（同 D7） |
| L11 | `requirementdependency` 未登记分区段 | 复合主键首段 `requirementID` 即 partitionId，但库侧无段（`@Partitioned [min,max]`）信息 |
