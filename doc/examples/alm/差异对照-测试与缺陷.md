# 差异对照：测试用例与缺陷（标准侧 vs `mmda_alm` 库侧）

> **用途**：把「现行规范里的**测试用例**与**缺陷**」与「`mmda_alm` 库里的 `testcase` / `teststep` / `testcasedependency` / `testtype` / `bug`」逐条摊开，交作者勾选哪些进标准。姊妹篇 = [`差异对照.md`](差异对照.md)（需求 / 意图，D0–D16 + L1–L11）。
> **取数**：标准侧 = [`../../lang/test.md`](../../lang/test.md)（草案）+ [`../../testing.md`](../../testing.md) §0.1 / §0.2 / §1 / §5 / §6 / §9 / §9.1 + [`../../lang/intent.md`](../../lang/intent.md) §4 / §6 + [`../../lang/project.md`](../../lang/project.md) §1.2 / §1.3 / §6 + [`../../quality.md`](../../quality.md) §5；库侧 = `mmda_alm` 五表**实测 DDL 与 C# 模型**（本机 `127.0.0.1:3306`，`D:\2026\cs\MMDA\Mmda.Alm\Mmda.Alm.Models`）。
> **一句话结论**：**库侧是一套「过程管理」的用例表（阶段 + 类型树 + 环境 + 人工位 + 步骤脚本 + 执行结果），标准侧是一套「可追溯 + 可验收」的用例声明（`req` / `covers` / `source` / `suite` / 生命周期）**——两边的**核心关切不同**：库关心「测试执行怎么管」，标准关心「验收依据怎么立、追溯链怎么闭合」。所以差异的主体是 **`③ 两边冲突`（T15–T19 + 两道总闸）**，其余是各自的补白。
> **⤴ 2026-09-29 四轮（作者裁）**：**`mmda_alm` 仅作参考，不再作为投影目标，将来废除**（作者原话：「**mmda_alm仅仅给你作参考，不用投影，以后废除了**」）——本表的定位从**「库侧该不该补」改成「旧库留给我们的设计输入」**：**①「只库有 → 要不要收进标准」仍然有效**（旧库是需求样本）、**③「两边冲突」仍作设计输入**；而 **②「只标准有 → 库里要不要补」与 ④「库自身不一致 → 要修」全部失效**（那个库不做了）。落库真源只剩内核 `MetaTest` 族（[`../../lang/test-store.md`](../../lang/test-store.md) §0）。
> **状态**：**草案（2026-09-29 立；同日二轮追加 §⑤：T20–T25）**。下表**未打勾的条目一律待裁**；库侧实测行只陈述事实，不含裁决。**T12 / T13 / T2 / T5 / T6 / T9 / T10 / T16 已被 §⑤ 修订**，**T23 于同日三轮改 BDD `given` / `when` / `then`**，**同日四轮：库侧整体降为参考（见下）**，勾选时以**四轮口径**为准。

## 0.5 库侧实测（摘要）

### `testcase`（24 列，PK `testCaseID`）

| 列 | 类型 | 注释（节选） |
| --- | --- | --- |
| `testCaseID` | bigint NOT NULL DEFAULT 0 | 测试用例ID |
| `testCaseNo` | varchar(30) NOT NULL | 测试用例编号 |
| `testPhase` | tinyint NOT NULL DEFAULT 0 | `0;UNIT;单元测试\|1;INTEGRATION;集成测试\|2;SYSTEM;系统测试\|4;UAT;验收测试` |
| `testTypeID` | int NOT NULL | `HAS_ONE TestType(testTypeID,testTypeName)` → `FK_testcase_testtype` |
| `testCaseDescription` | varchar(255) NOT NULL | 测试用例描述 |
| `moduleCode` | varchar(15) NOT NULL | `REF metadata.Module(moduleCode,moduleLabel)` |
| `importance` / `priority` | tinyint NOT NULL DEFAULT 0 | `UNKNOWN/IMPORTANT/VERY_IMPORTANT` / `NORMAL/SENIOR/URGENT` |
| `environment` | tinyint NOT NULL DEFAULT 0 | `DEV / TEST / PROD` |
| `manual` | bit(1) NOT NULL DEFAULT b'0' | 人工测试 |
| `preCondition` | varchar(255) NULL | 预置条件 |
| `inputData` | text NOT NULL | 输入数据 |
| `expectedResult` | varchar(255) NOT NULL | 预期结果 |
| `actualResult` | varchar(255) NOT NULL | 实际结果 |
| `status` | smallint DEFAULT 0（**可空**） | `0;NOT_TEST;未测试\|1;PASS;通过\|-1;FAILED;失败` |
| `tags` | varchar(255) **utf8_general_ci** | 标签 |
| `revision` | int NOT NULL DEFAULT 0 | 修订版本 |
| 审计 7 件套 | `deptID` / `creatorID` / `createDate` / `lastModifierID` / `lastModified` / `ownerID` / `ownerDeptID` | 与 `bom` / `bug` 表**完全相同** |

索引：`PRIMARY(testCaseID)` + `testCaseNo` / `testPhase` / `moduleCode` / `importance` / `priority` / `environment` / `status` / `lastModified` 各普通索引 + `FK_testcase_testtype`。**表注释**：`@TestCase 测试用例。包含基本的八项要素，用例编号、测试项目、标题、重要性、预置条件、输入、操作步骤、预期输出`。

### `teststep`（PK `testCaseID` + `testStepID`）

`desctiption` varchar(255) NOT NULL / `testScript` varchar(2048) NULL；`FK_step_testcase`（`ON DELETE CASCADE ON UPDATE CASCADE`）。

### `testcasedependency`（PK `testCaseID` + `preTestCaseID`）

注释：`HAS_ONE TestCase(testCaseID,testCaseNo,testCaseTitle) AS preTestCase`；`FK_dependency_testcase`（CASCADE）/ `FK_pre_testcase`（**仅 `ON UPDATE CASCADE`**）。

### `testtype`（20 行，两级树）

`testTypeID` / `testTypeName` / `description` / `superTestTypeID`（**无 FK**）。实测树：`1 功能测试` → `11 单元` / `12 集成` / `13 系统` / `14 验收`；`13 系统` → `130 冒烟` / `131 黑盒` / `132 端到端`；`11 单元` → `111 白盒`；`12 集成` → `121 灰盒`；`2 非功能测试` → `21 安全` / `22 性能` / `23 可用性` / `24 兼容性`；`21` → `211 穿透`；`22` → `220 负载` / `221 压力` / `223 扩容性` / `224 浸泡`。

### `bug`（18 列，PK `bugID`）

`bugTitle` varchar(255) NOT NULL / `bugDetails` text NULL / `urgency` / `severity`（`UNDEFINED/MINOR/MEDIUM/CRITICAL/FATAL`）/ `status`（`NEW/OPEN/FIXED/REOPEN/CLOSED/REJECTED/ABANDON`）/ `moduleCode` NOT NULL / `moduleVersion` int NULL / `tags` / 审计 7 件套 / **`testCaseID` bigint NULL** / **`testStepID` int NULL**（**两者均无外键**）。

## ① 只库有：要不要进标准？

### T1 · 测试阶段 `testPhase`
| | |
| --- | --- |
| 标准（现状） | 无独立阶段轴；[`../../testing.md`](../../testing.md) §9.1 的 `kind` 平铺枚举里混有 `uat` / `integration` |
| 库 | `testPhase` tinyint：`UNIT` / `INTEGRATION` / `SYSTEM` / `UAT`（值 `0/1/2/4`，**3 空档**） |
| 建议 | **进标准**（[`test.md`](../../lang/test.md) §2.2 提议 `phase` 轴）；库侧值域有空档 ⇒ 建议 `mmda check` 只认符号名 |

### T2 · 测试类型树 `testtype`（**表**，不是枚举）
| | |
| --- | --- |
| 标准 | `kind` 是**内核封闭枚举**（[`test.md`](../../lang/test.md) §2.2） |
| 库 | `testtype` 独立表 + 自引用树（`superTestTypeID`），20 行两级 |
| 建议 | **分两层**：内核 `kind` 封闭枚举（门禁可判定）+ 应用侧 `TestType` 记录（自加类型）；**不要把 20 行树搬进语言**（收 L7 的「枚举与字典表口径不统一」） |

### T3 · 测试环境 `environment`
| | |
| --- | --- |
| 标准 | 无（但性能阈值**已裁按环境分档**，[`../../testing.md`](../../testing.md) §11-6） |
| 库 | `DEV` / `TEST` / `PROD` |
| 建议 | **进标准**（`env`，[`test.md`](../../lang/test.md) §2.3）；库侧 `PROD` 与「UAT 跑在生产」冲突时需明确口径 |

### T4 · 人工测试 `manual`（bit）
| | |
| --- | --- |
| 标准 | `source: manual` = **手写用例**（vs 机械 / AI 生成） |
| 库 | `manual` bit(1) = **人工执行**（vs 自动执行） |
| 建议 | **语义不同名** ⇒ 见 **T19**（拆 `source` × `driver`） |

### T5 · 四列拆法（预置 / 输入 / 预期 / 实际）
| | |
| --- | --- |
| 标准（[`../../lang/test.md`](../../lang/test.md) §3） | `given` / `when` / `then` 三块（**v3**） |
| 库 | `preCondition` / `inputData` / `expectedResult` / `actualResult`；**无 `when` 列**（操作步骤在 `teststep`） |
| 建议 | 标准取 `given` / `when` / `then`（**`when` 必须在**：无步骤的用例不可执行）；`actualResult` 归**执行面**（**T15**） |

### T6 · 步骤子表 + 可执行脚本 `teststep` / `testScript`
| | |
| --- | --- |
| 标准 | 无脚本要素；[`../../testing.md`](../../testing.md) §0.1 定「执行通道 = hooks + `mmda test`」 |
| 库 | `teststep`（有序步）+ `testScript` varchar(2048)（可执行片段） |
| 建议 | **`testScript` 是执行面落地**（`driver: HOOKS/E2E` 的驱动配置 + `MetaTestRun`），**不进语言文件**（[`test-store.md`](../../lang/test-store.md) §8.2） |

### T7 · 用例依赖 `testcasedependency`
| | |
| --- | --- |
| 标准 | 无（[`../../testing.md`](../../testing.md) §6.2-3 只要求**独立可重放**） |
| 库 | 自引用 M:N（`testCaseID` → `preTestCaseID`）+ 级联 |
| 建议 | 进标准（`depends TC-…`）；⚠️ 与「独立可重放」冲突时以后者优先——`depends` 只表达**前置数据/前置动作**，不表达执行顺序 |

### T8 · 重要性 / 优先级两列
| | |
| --- | --- |
| 标准 | 用例侧未定 |
| 库 | `importance`（3 档）+ `priority`（3 档，即 urgency 口径） |
| 建议 | **进标准**，**与 `intent` 同名同值域**（`importance` × `priority`，[`test.md`](../../lang/test.md) §2.3）——单字段表达不了「重要但不急」（同差异 D4） |

### B1 · 缺陷详情 `bugDetails`
| | |
| --- | --- |
| 标准 | 无缺陷要素（追溯链上只有节点名） |
| 库 | `bugTitle` varchar(255) + `bugDetails` text（标题 / 正文分离） |
| 建议 | 走 **`/// <label> : <description>`** 口径（同 **T18** / 差异 D9） |

### B2 · 严重性 `severity`（五档，与 `urgency` 正交）
| | |
| --- | --- |
| 标准 | 无 |
| 库 | `severity`：`UNDEFINED` / `MINOR` / `MEDIUM` / `CRITICAL` / `FATAL`（`Mmda.Core.Enums` 共用列） |
| 建议 | **进标准**——**「严重性 × 紧急性」是缺陷的两维**，同 `intent` 的 `importance` × `urgency`（D4）；单维会把「致命但不急」压成一处 |

### B3 · 发现版本 `moduleVersion`
| | |
| --- | --- |
| 标准 | 无（但有 `baseline/<版本>` 冻结机制，[`../../testing.md`](../../testing.md) §5） |
| 库 | `moduleVersion` int NULL |
| 建议 | 进标准为 `foundIn: <baseline 版本>`——**缺陷必须能指回它是打破哪一版验收基线的**（否则回归覆盖无意义） |

### T13 · `covers:` + 双签 `reviewedBy` + 分层 `level`
| | |
| --- | --- |

## ③ 两边冲突：必须二选一 / 定分工

### T0 · 用例的本质（**总闸**）
| | |
| --- | --- |
| 标准（[`../../testing.md`](../../testing.md) §9.1） | **用例进 m 语言 + 进库**：文件（`tests/*.m`，git）**唯一真源** → 落内核元对象（`MetaTest` 族）→ IDE 直读管理面；运行期在库里改了必须回写文件 |
| 库 | `testcase` 是**应用业务表**：用例由人在 ALM 里直接建、直接改，**没有文件真源、没有编号签发机制** |
| 冲突 | **真源的归属**——「谁说了算」定不下来，T11 / T12 / T13 / T15 都没法落 |
| 选项 | **A** 元对象路线（同 `MetaIntent`，D0 = A 的先例）／ **B** 应用业务表（库里是真源，语言侧只做导入导出）／ **C** 并存 + 定主从（文件为主、库为投影） |
| 建议 | **A**（与 ✔ 2026-09-28 已裁的意图路线一致；~~`testcase` 降为**投影 / 缓存**~~ —— **⤴ 四轮：`mmda_alm` 将废除，「降为投影」取消，只留参考**） |

### T15 · 状态轴：库一轴（执行态） vs 标准两轴（生命周期 + 执行）
| | |
| --- | --- |
| 标准 | **生命周期**（draft / reviewed / frozen / deprecated，工具管）＋ **执行**（not-run / pass / fail / blocked / stale），两轴正交 |
| 库 | 单列 `status`（`NOT_TEST` / `PASS` / `FAILED`）——**只有执行态**；且 `smallint DEFAULT 0` **可空**（收 L15） |
| 冲突 | ① 库里「已冻结的用例」无处可查，而它才是**验收依据**；② 一条用例**跑很多次**，一列存不下历史（三端 × 每日 × 里程碑） |
| 选项 | **A** 加 `lifecycle` 列 + 执行迁 `MetaTestRun`（**推荐**）／ **B** 保持一列，接受验收依据不可查 |
| 建议 | **A** |

### T16 · 分类轴：库两轴重复 vs 标准一轴平铺
| | |
| --- | --- |
| 标准 | 单轴 `kind` 平铺（`uat` / `smoke` / `api` / `functional` / `integration` / `perf` / `security` / `conformance`） |
| 库 | **两处表达同一件事**：`testcase.testPhase`（`UNIT/INTEGRATION/SYSTEM/UAT`）与 `testtype` 树第二层（`11 单元` / `12 集成` / `13 系统` / `14 验收`）**逐项对应** |
| 冲突 | 「阶段」被表达了两遍；而标准的平铺 `kind` 又把 `uat` / `integration` 塞进了「类型」 |
| 选项 | **A** 分两轴：`phase`（阶段）+ `kind`（视角，去掉 `uat` / `integration`）（**推荐**，[`test.md`](../../lang/test.md) §2.2）／ **B** 只留一轴（废 `testPhase`）／ **C** 两轴并存但不互相约束 |
| 建议 | **A** |

### T17 · 编号：库形态自由且不唯一 vs 标准内核签发
| | |
| --- | --- |
| 标准 | `TC-<NNN>` 纯序号，**内核签发**、单调、不复用（[`test.md`](../../lang/test.md) §3） |
| 库 | `testCaseNo` varchar(30) NOT NULL，**只有普通索引**（`IDX_testcase_no`，非唯一）；形态无约定 |
| 冲突 | 编号是追溯链的**稳定锚**（`req` / `covers` / 缺陷回指都指向它），可重号即追溯可造假 |
| 选项 | **A** `TC-<NNN>` + UNIQUE（**推荐**，收 L13）／ **B** 保留应用自定义编号，另加内核 `testID` 作锚 |
| 建议 | **A** |

### T18 · 标题 / 描述 / 正文的落法
| | |
| --- | --- |
| 标准 | `/// <label> : <description>`（label = 业务可读标题，**验收单由它生成**）+ 正文 `given` / `when` / `then` |
| 库 | **一列 `testCaseDescription` varchar(255) NOT NULL 兼任标题与描述**；且**表注释写有「标题」但表中无 `testCaseTitle` 列**（另见 L12），**正文的「操作步骤」在另一张表** |
| 冲突 | 验收单需要「一句话标题」；255 字符单列既装标题又装描述，机器无法分辨 |
| 选项 | **A** 拆 `label` + `description`（**推荐**，同差异 D9 的 A 案）／ **B** 维持单列（则验收单标题由截断生成） |
| 建议 | **A** |

### T19 · `manual` 同名不同义（生成 vs 执行）
| | |
| --- | --- |
| 标准 | `source: manual` = **谁写的**（`mechanical` / `snapshot` / `ai` / `manual`，✔ 已裁 [`../../testing.md`](../../testing.md) §1） |
| 库 | `manual` bit(1) = **怎么跑**（人工测试 vs 自动） |
| 冲突 | 同一个词，两个轴。写成 `source: manual` 的**手写 UAT** 在库里与「人工执行」是**两回事**，同名会导致投影时悄悄错位 |
| 选项 | **A** 拆轴：`source`（谁写）× `face`（验哪个面：`UI` / `API`）× `driver`（`E2E` / `HTTP` / `HOOKS` / `MANUAL` 怎么跑，**v5 值域**、与 `face` 配对）（**推荐**，[`test.md`](../../lang/test.md) §2.2 / §2.3）／ **B** 保留 `manual` 一位、另立列给 `source` |
| 建议 | **A** |

### B0 · 缺陷的本质（**总闸**）
| | |
| --- | --- |
| 标准 | 缺陷只是**追溯链上的一个节点名**，无语言要素、无门禁、无落点 |
| 库 | `bug` 是**独立业务表**（18 列）：标题 / 详情 / 紧急 / 严重 / 7 态状态 / 模块 / 版本 / 标签 / 审计 + 源用例指针 |
| 冲突 | 缺陷要不要成为**语言一等要素**（`defect` + `BUG-<NNN>` + `MetaDefect`） |
| 选项 | **A** 进语言／ **B** 应用侧 `record Defect` + `stm DefectStatus`，语言只提供编号引用（**推荐**，[`test.md`](../../lang/test.md) §6）／ **C** 保持现状（库侧断链） |
| 建议 | **B**——缺陷是**运行期产物**（量大、随时生成），按「状态归 `stm`」与「应用业务对象走 `record`」两条既有口径，它不该进语言要素 |

### B5 · 缺陷状态：库硬编码 7 态 vs 标准「状态归 stm」
| | |
| --- | --- |
| 标准 | 「**状态归 `stm`**」（同 [`差异对照.md`](差异对照.md) **D5**）：状态取值与迁移写在 `stm` 声明里，`mmda check` 管迁移 |
| 库 | `bug.status` tinyint NOT NULL + **注释里的 7 态**（`NEW/OPEN/FIXED/REOPEN/CLOSED/REJECTED/ABANDON`，正负号混用） |
| 冲突 | 取值域在**列注释**里重复一份（收 L8 同款）；迁移（谁能从哪到哪）**完全没有表达** |
| 建议 | 状态与迁移移入 `stm DefectStatus`；库侧 `status` 只存投影值 |

### B6 · 缺陷归属与版本
| | |
| --- | --- |
| 标准 | 归属由**回指反查**得出（`req` / `covers`），不写 `moduleCode`（同 T12 / 差异 D3） |
| 库 | `moduleCode` NOT NULL + `moduleVersion` NULL |
| 冲突 | 归属的**真源方向**：库里写死 vs 由需求 / 用例反查下推 |
| 建议 | 归属反查下推（同 T12）；**`moduleVersion` 语义收窄为 `foundIn`（打破哪一版基线）**并进标准（**B3**） |
